## Подготовка среды

1. Проверить Git status и инструкции проекта.
2. Проверить доступность WSL2 и нужного дистрибутива. Сначала чтение состояния; не запускать восстановительные аппаратные действия по старой команде.
3. Найти существующий NANOX checkout в WSL, если он есть. Сравнить историю и незакоммиченные файлы.
4. Если его нет, подготовить рабочую копию на Linux filesystem, например `~/src/NANOX-OS`, сохранив историю и все нужные изменения текущего checkout. Простой clone не переносит незакоммиченные документы: проверить их отдельно.
5. Записать выбранный абсолютный путь в локальное описание среды. Не вести две расходящиеся основные копии.
6. Проверить Nix, доступность требуемых пакетов и возможность получить закреплённый Rust с двумя target libraries.

Работа с файлами Linux из Linux-среды соответствует [рекомендациям Microsoft для WSL](https://learn.microsoft.com/en-us/windows/wsl/filesystems). Если WSL реально неисправен, сообщить конкретную ошибку и продолжать независимую подготовку исходников. Это не повод автоматически трогать физические диски.

## Планируемый интерфейс команд

Следующие команды предстоит реализовать; это не утверждение об их текущей доступности:

```sh
nix develop
cargo xtask doctor
cargo xtask build
cargo xtask run
cargo xtask test
cargo xtask test --replay
cargo xtask debug --run <run-id>
```

`test` запускает host-проверки и обычные QEMU-сценарии. `test --replay` дополнительно записывает реальный replay trace и воспроизводит его. Debug не входит в автоматический test: он может останавливаться на breakpoint.

`nix develop` не подменяет target libraries случайно установленным rustup. `flake.lock` сам по себе не фиксирует подвижное `channel = "stable"`: версия Rust и источник toolchain фиксируются явно. Nix inputs и Cargo зависимости блокируются своими lock-файлами. [Flakes](https://nix.dev/concepts/flakes.html) используются как механизм упаковки среды.

При работе с Git flake убедиться, что Nix видит новые исходные файлы. Не использовать молча устаревшее содержимое из другого checkout или staged snapshot; способ подачи source tree должен быть описан и проверен. Не создавать коммит автоматически только для обхода этой особенности.

## Порядок законченных изменений

1. Toolchain, `doctor`, workspace, target-specific build и локальный `.gitignore`.
2. PE/COFF loader и реальный тест его запуска в OVMF.
3. ELF parser с негативными host-тестами.
4. Загрузка сегментов, BootInfo, page tables и переход в ядро.
5. Kernel serial, boot info validation, test-only debug exit.
6. Harness с timeout, отрицательными сценариями и RunRecord.
7. Repeat-build и record/replay, включая одинаковое исходное состояние firmware/дисков.
8. Обновление статуса и документации фактическими командами, хешами и логами.

Наличие частичного boot считается промежуточным результатом. Не объявлять M0 завершённым, пока не выполнены критерии ниже.

## Критерии M0

- [ ] Из чистого checkout в выбранной среде работает документированная цепочка сборки.
- [ ] QEMU запускает собственный UEFI loader и собственное ELF-ядро.
- [ ] Ядро получает и проверяет BootInfo после `ExitBootServices`.
- [ ] Serial содержит маркеры loader/kernel и итоговый PASS.
- [ ] Harness правильно интерпретирует `isa-debug-exit` и timeout.
- [ ] Повреждённый ELF отвергается loader, успешное ядро при этом не имитируется.
- [ ] Намеренно неуспешный kernel/test приводит к FAIL, не к зелёному тесту.
- [ ] Две чистые сборки дают одинаковые хеши `.efi` и `.elf` при одинаковом source/toolchain.
- [ ] Отдельный replay-прогон воспроизводит записанный запуск с тем же сырым serial-логом и вердиктом.
- [ ] Сохранены команды, RunRecord, firmware/image hashes, логи и replay trace.

Если выбранная комбинация QEMU/OVMF не поддерживает нужный replay-профиль, не подменять replay двумя обычными запусками. Выделить воспроизводимый сбой, испытать минимальную совместимую конфигурацию и записать результат. M0 остаётся неполным по этому пункту до его решения либо явного изменения критерия пользователем.
