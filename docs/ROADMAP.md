# Этапы и критерии готовности

Чекбоксы отмечаются только по фактическим проверкам; ссылки на них — в [STATUS](STATUS.md). Порядок выбран так, чтобы собственная ОС и управление ИИ появились до IDE, GPU и собственного compiler.

## Зависимости

```text
M0 boot → M1 kernel foundations → M2 userspace/IPC → M3 AI bridge
                                                   ↓
                              M4 storage → M5 network/native API
                                                   ↓
                              M6 OS updates → M7 desktop/Studio/VPN
                                                   ↓
                              M8 local CPU inference

M9 hardware/SMP: после M2, драйверов M4–M5 и отдельного hardware profile.
M10 self-hosting: после M6 и достаточного userspace/runtime; полная offline-цепочка требует M8.
R research: после работающих базовых контрактов, независимо от критического пути.
```

## M0 — среда и вертикальная загрузка

Состав: [START-HERE](START-HERE.md), [BOOT-M0](specs/BOOT-M0.md), [TESTING-REPLAY](specs/TESTING-REPLAY.md).

- [x] Проверить среду и определить один основной Linux checkout.
- [x] Зафиксировать toolchain, firmware, machine и CPU profile.
- [x] Реализовать `cargo xtask doctor/build/run/test/debug`.
- [x] Собственный loader загружает ELF, завершает Boot Services и передаёт управление ядру.
- [x] Ядро проверяет BootInfo и пишет собственный serial report.
- [x] PASS, FAIL и timeout различаются автоматически.
- [x] Некорректный ELF отвергается до handoff.
- [x] Проверена повторяемость бинарных сборок.
- [x] Настоящий replay воспроизводит записанный serial побайтно.
- [x] Сохранён полный RunRecord и обновлён STATUS.

Артефакт: загрузочный файловый образ и результаты проверок. Не включает полноценные allocator, userspace, сеть или ИИ.

## M1 — память, прерывания и планирование

- [ ] Физический allocator исключает kernel, loader handoff, tables и reserved/device memory.
- [ ] Реализованы mapping/unmapping и проверка page permissions.
- [ ] Heap имеет проверяемые границы и диагностику ошибок.
- [ ] GDT/IDT, исключения, timer и аварийный стек работают независимо от firmware.
- [ ] Переключаются минимум два kernel threads; CPU-bound поток вытесняется.
- [ ] Проверены guard pages, page fault, double free и исчерпание памяти.
- [ ] Время и внешние события имеют явные abstraction boundaries и trace IDs.

Артефакт: работающее основание ядра. Однопроцессорность не выдаётся за отсутствие races.

## M2 — userspace, objects, rights, IPC

- [ ] Userspace ELF запускается в ring 3 с отдельным адресным пространством.
- [ ] Работают безопасные syscall entry/return и проверка пользовательских буферов.
- [ ] Схема ABI порождает типы и тестовые golden fixtures.
- [ ] Handles, subset duplicate, закрытие и generation checks реализованы.
- [ ] IPC поддерживает reply, timeout, peer death и notifications.
- [ ] Обычная задача не получает чужую память или Sovereign authority.
- [ ] Init получает bootstrap authority от ядра и передаёт права исполнителю Core.
- [ ] Привилегированное тестовое действие действительно доступно Sovereign.
- [ ] Некорректный syscall и смерть приложения не останавливают ядро.

Артефакт: собственная объектная ОС с изоляцией обычных программ и полноправным системным субъектом.

## M3 — замкнутый цикл ИИ через bridge

- [ ] Реализован framed COM2 protocol с лимитами и version negotiation.
- [ ] Host bridge и guest executor имеют раздельные обязанности.
- [ ] Подключена одна настоящая модель через выбранный adapter.
- [ ] По запросу ИИ получает список задач, запускает нагрузку, измеряет и останавливает её.
- [ ] Verifier проверяет состояние задачи после операции.
- [ ] Отработаны stale object, duplicate request, потерянный ответ и отмена.
- [ ] События имеют sequence, overflow marker и resync.
- [ ] Сбой provider сохраняет recovery shell и не блокирует ядро.
- [ ] Replay использует сохранённые входы модели, а не повторный API-запрос.

Артефакт: настоящий ИИ управляет собственным guest kernel. История на этом этапе может сохраняться host harness; reboot-resume внутри guest появляется после M4.

## M4 — постоянное состояние

- [ ] Userspace virtio-blk driver и block protocol работают.
- [ ] Определены on-disk format, checksums, commit и recovery.
- [ ] Object store сохраняет данные, конфигурацию и задачи Core.
- [ ] После reboot задачи восстанавливаются по определённой семантике.
- [ ] Проверены torn writes, cutpoints, full disk, corrupt metadata и GC.
- [ ] Snapshot/restore проверены для обозначенного набора объектов.

Артефакт: durable state. История не обещает отмену внешних эффектов.

## M5 — сеть, ключи и нативный API provider

- [ ] Userspace virtio-net и необходимые Ethernet/IP/UDP/TCP/DNS механизмы.
- [ ] Проверены потери, reorder, malformed packets, ресурсные лимиты и timers.
- [ ] Работают entropy/CSPRNG и проверенные криптографические операции.
- [ ] TLS проверяет сертификаты относительно trust store и определённой политики времени.
- [ ] API credentials хранятся и используются без вывода в обычные логи.
- [ ] Core вызывает provider непосредственно из NANOX без host bridge.
- [ ] Обрывы streaming, timeout и reconnect не дублируют системный эффект.

Артефакт: самостоятельный сетевой клиент ИИ. Local inference ещё не обязателен.

## M6 — обновление самой ОС

- [ ] Build service связывает source snapshot, toolchain и артефакты.
- [ ] Core создаёт патч и инициирует сборку на явно внешнем builder.
- [ ] Кандидат проходит отдельный QEMU test run.
- [ ] Работают manifest Generation, trial boot, accept и выбор последней рабочей версии.
- [ ] Зависший/неработающий кандидат восстанавливается через проверенный watchdog/reset путь.
- [ ] Data migrations имеют совместимость или отдельный путь восстановления.
- [ ] Показаны успешное обновление и преднамеренно неуспешное обновление.

Артефакт: полный цикл изменения собственной ОС; native self-hosting не заявляется.

## M7 — рабочая среда, Studio и VPN

- [ ] Framebuffer/input/compositor и собственный UI toolkit.
- [ ] Текст, Unicode, редактирование, focus, clipboard и semantic tree.
- [ ] Shell, чат, файлы, настройки и просмотр событий.
- [ ] Studio связывает исходник, diagnostic, patch, build и запущенную версию.
- [ ] Пакеты устанавливаются через проверяемое изменение поколения.
- [ ] Tunnel работает с независимым VPN peer; проверены replay/rekey/MTU/DNS/route failure.
- [ ] Пользователь завершает целевой сценарий целиком через интерфейсы NANOX.

Артефакт: пригодная для ограниченного практического сценария среда разработки.

## M8 — локальный ИИ на CPU

- [ ] Выбраны конкретные веса, лицензия использования, tokenizer и формат.
- [ ] Реализован минимальный tensor runtime и требуемые операции.
- [ ] Вывод сопоставлен с независимым reference с подходящей численной точностью.
- [ ] Измерены RAM, first-token latency, скорость и качество задач.
- [ ] Core выполняет контрольные задачи без сети.
- [ ] Ошибки/OOM inference восстанавливаются без потери системы.

Артефакт: нативное локальное выполнение конкретной модели. GPU не подменяет отсутствующий CPU/reference путь.

## M9 — физическое железо, SMP и устройства

- [ ] Выбран один точный hardware profile; записаны устройства/firmware.
- [ ] Boot, ACPI/PCI, interrupt routing и необходимые драйверы проверены на нём.
- [ ] SMP поддерживает per-CPU state, синхронизацию и TLB shootdown.
- [ ] DMA lifetimes и IOMMU проверены в поддержанной конфигурации.
- [ ] Device reset и recovery имеют фактические тесты.
- [ ] GPU display/compute внедряются отдельно и только для выбранного устройства.

Артефакт: перечисленная аппаратная поддержка. Не утверждать совместимость со всеми ПК.

## M10 — самостоятельная разработка и испытания

- [ ] Определён native userspace target и необходимый runtime/libc/std слой.
- [ ] Compiler/linker/build tools реально работают внутри NANOX.
- [ ] ОС пересобирает собственные компоненты и загрузочный образ.
- [ ] Портирован эмулятор или реализован ограниченный VMM для тестирования кандидатов.
- [ ] Внутри NANOX выполнены успешное обновление и неудачный кандидат с recovery.
- [ ] С M8 выполнена offline-цепочка: запрос → код → сборка → испытание → обновление.

Артефакт: self-hosting с явно перечисленными внешними зависимостями. Собственный compiler — отдельная последующая работа, даже если портированный compiler уже работает.

## R — исследовательские результаты

- [ ] Ограниченная IR-семантика и минимум две согласованные реализации.
- [ ] Проверяемые свойства конкретных компонентов и версии доказательств.
- [ ] Воспроизводимость выбранного runtime-сценария с записанными входами.
- [ ] Планирование по зависимостям с измерением относительно baseline.
- [ ] Собственный формат/ISA/compiler только с доказанной пользой для задачи.
- [ ] Отчёты содержат ограничения, затраты и отрицательные результаты.

## Общий Definition of Done

Для этапа нужны работающий сценарий, негативные проверки существенных границ, сохранённые артефакты и обновлённый статус. Дата, количество строк или красивый интерфейс не заменяют критерий готовности.
