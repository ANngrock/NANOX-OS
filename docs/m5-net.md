# M5: сеть и автономный provider — virtio-net, свой стек, TLS 1.3, агент в госте

Документ фиксирует решения этапа M5 (ARCHITECTURE.md §15) и то, чем
подтверждён каждый критерий. Стенд, harness и коды выхода —
[m0-bench.md](m0-bench.md); NCI, исполнитель `bin/core` и task engine —
[m3-core.md](m3-core.md); хранилище, из которого берутся конфигурация,
ключ и якоря доверия, — [m4-store.md](m4-store.md). ARCHITECTURE.md задаёт
цель («собственная ОС взаимодействует с моделью через свой сетевой стек;
телеметрия различает сетевой сбой, ошибку provider и ошибку выполнения
действия»); выбор устройств, объём стека, набор криптографии, протокол
provider, классы ошибок и стенд — решения M5 (раздел 12).

**Готовность M5** («собственная ОС взаимодействует с моделью через свой
сетевой стек; телеметрия различает сетевой сбой, ошибку provider и ошибку
выполнения действия») **подтверждена с тестовым provider**: в QEMU (TCG)
`bin/core` сам разрешает имя, открывает TCP и TLS 1.3 со своей проверкой
сертификата, отправляет запросы протокола Messages и разбирает потоковый
ответ; сценарий `m5-classes` получает у одного и того же гостя
`NET_ERROR` (отказ в соединении, опущенный линк), `PROVIDER_ERROR` (HTTP
400, вызов несуществующего инструмента) и `ACTION_ERROR` (исполнитель
провалил действие модели) — в ответе, в строках телеметрии и в счётчиках
`telemetry.status`; с выключенной классификацией (`m5-flattel`) проверки
проваливаются. Тестовый provider — сценарная политика, **не языковая
модель**; с настоящим provider путь не проверялся — в среде нет ключа
(раздел 14).

## 2. Компоненты и граница

```text
 host (стенд)                             │ guest (QEMU, TCG)
                                          │
 m5scripts.py ── COM2 (NCI) ──────────────┼──► bin/core: консоль оператора
   печатает REQ, сверяет ответы,          │      agent.ask ─► agent.c ─► task engine (M3)
   журнал и то, что видели сервисы        │                     │
                                          │               provider.c ─► lib/http (JSON/HTTP/SSE)
 provider.py  (HTTPS, OpenSSL) ◄──────────┼── m5tls.c ─► lib/tls (TLS 1.3, X.509) ─► lib/crypto
 m5host.py: DNS, echo, TLS echo           │   lib/net (ARP/IPv4/ICMP/UDP/DNS/TCP)
 QMP set_link ─► QEMU user net (slirp) ◄──┼── вызовы 26–28 ─► virtio-net
                                          │   вызов 29 ─► virtio-rng; вызов 30 ─► RTC
```

- Ядро даёт только кадры, энтропию и часы (вызовы 26–30); все протоколы,
  TLS и provider — код пользовательского процесса `bin/core`. Стек и
  криптография — чистый код (`lib/net`, `lib/crypto`, `lib/tls`,
  `lib/http`), тот же исходник собирается в host-тесты.
- Host в цикле агента не участвует: он печатает `agent.ask` в консоль и
  читает ответ, как оператор. Модель спрашивает гость, сетевые пакеты идут
  через virtio-net и user-mode сеть QEMU (slirp) на `10.0.2.2` — loopback
  хоста, где слушают сервисы стенда.
- Мост M3 (`tools/bridge`, адаптеры host) остаётся для сценариев M3; в M5
  он используется только как консоль.

## 3. Устройства: virtio-net, virtio-rng, часы

- **Транспорт.** `kernel/dev/virtio.c` — общий для virtio-blk (M4 переведён
  на него без изменения поведения), virtio-net и virtio-rng: capabilities
  PCI, согласование `VERSION_1`, split-очереди, опрос без прерываний.
- **virtio-net.** Возможности `VERSION_1`, `MAC`, `STATUS`; без offload и
  mergeable buffers: каждый кадр — целый кадр Ethernet ≤ 1514 байт за
  12-байтным заголовком. 16 страниц приёма постоянно в очереди 0, передача
  по одному кадру с ожиданием завершения. Состояние линка — поле `STATUS`
  конфигурации (QMP `set_link name=nxnet`). Объект `NX_OBJ_NETDEV`, права
  READ (приём, сведения) и WRITE (передача); без линка передача отвечает
  `NX_ENOLINK`.
- **Тестовый слой потерь** (только тестовые режимы): `nanox.m5.loss=rx:N,tx:M`
  отбрасывает каждый N-й принятый и M-й отправленный кадр,
  детерминированно; счётчики — в `net.status`.
- **virtio-rng.** Одна очередь запросов; источник — `rng-builtin` QEMU
  (getrandom хоста). Вызов 29 отдаёт сырые байты; обработка — в `bin/core`
  (раздел 6).
- **Часы.** CMOS RTC читается при загрузке; вызов 30 даёт тики и Unix-время
  (нужно для срока действия сертификатов). Стенд задаёт RTC QEMU
  `base=2026-01-01,clock=vm`, поэтому время гостя воспроизводимо.
- **QEMU.** `-netdev user,ipv6=off` (без root и tap), фиксированный MAC,
  `romfile=` (без iPXE), QMP-сокет в каталоге запуска.

## 4. Сетевой стек (`lib/net`)

Однопоточный, опросный: каждая блокирующая функция крутит `net_poll()`
(принять кадр, обработать, запустить таймеры) до условия или срока.

- Ethernet II, ARP (кэш 8 записей, повтор 500 мс), IPv4 без фрагментации
  (фрагменты отбрасываются), ICMP echo (ответ и `net.ping`), UDP (4 сокета),
  DNS-клиент (A-записи, повтор, NXDOMAIN — `dns_notfound`), TCP (4
  соединения).
- **TCP**: MSS 1460, окно отправки ограничено 10 сегментами без контроля
  перегрузки, RTO 200–8000 мс с экспоненциальной задержкой, быстрая
  повторная передача по трём дубликатам ACK и частичным ACK (NewReno),
  буфер 8 сегментов вне порядка у получателя, пробы нулевого окна,
  сокращённый TIME_WAIT (500 мс). Соединение без подтверждения данных после
  7 повторов — `unacked_timeout`.
- Тайм-аут соединения — 15 с: slirp повторяет потерянный SYN-ACK лишь через
  ~6 с, а на повторный SYN отвечает голым ACK; более короткий срок
  превращал бы одну потерю в отказ (найдено сценарием `m5-net-loss`).
- Отрицательный контроль `m5-noretx` выключает повторную передачу (и
  быструю); при той же потере сценарий агента проваливается.
- Конфигурация — объекты `cfg/net.ip`, `net.mask`, `net.gw`, `net.dns`,
  `net.dns_port` хранилища; по умолчанию адреса slirp (`10.0.2.15/24`, шлюз
  `10.0.2.2`, DNS `10.0.2.3`). Стенд подставляет свой DNS-сервер.

## 5. Диагностика (операции NCI)

| Операция | Что делает |
| --- | --- |
| `net.status` | линк, адреса, счётчики устройства и тестовых потерь, TCP (повторы, соединения), часы |
| `net.ping target=` | ICMP echo через ARP следующего узла |
| `net.resolve name=` | DNS A-запрос к настроенному серверу |
| `net.probe host= port= text=` | TCP-соединение, строка туда и обратно (echo-сервер стенда) |
| `rng.status` | источник, тесты здоровья, состояние DRBG, два выхода различаются |
| `tls.probe host= port= [suites=]` | DNS, TCP, TLS 1.3 с проверкой, строка туда и обратно; набор, подпись, длина цепочки или классифицированный отказ |
| `provider.status` | хост, порт, модель, ссылка на ключ и его длина (не значение), состояние соединения, число якорей |
| `telemetry.status` | исходы по классам с загрузки, попытки, повторы, переподключения, запросы и действия |
| `agent.ask qa= [qb= qc=]` | цикл агента (раздел 8.4) |

Все они проходят жизненный цикл task engine M3 и отвечают в формате NCI;
отказ сети/TLS/provider — `FAILED code=<КЛАСС>_ERROR detail=<имя>
class=<класс>` (раздел 9).

## 6. Энтропия, CSPRNG и криптография

- **Энтропия → DRBG.** 48 байт с virtio-rng проходят тесты здоровья
  SP 800-90B (repetition count, порог 16; adaptive proportion, окно 512,
  порог 64; до трёх попыток), затем HMAC-DRBG (SHA-256, SP 800-90A) с
  персонализацией (boot id, время).
  Пересев — каждые 4096 запросов. Без исправного источника TLS не работает
  (`LOCAL_ERROR entropy`), а стек берёт номера портов и ISN из часов.
- **Примитивы** (`lib/crypto`): SHA-256/384/512, HMAC, HKDF, AES-128-GCM,
  ChaCha20-Poly1305, X25519, модульная арифметика Монтгомери, RSA PKCS#1
  v1.5 и PSS (проверка), ECDSA P-256/P-384 (проверка). Только проверка
  подписей — клиенту не нужно подписывать. Код не претендует на постоянное
  время для RSA/ECDSA-проверки (открытые данные); AEAD и X25519 написаны без
  ветвлений по секрету, но это не проверялось измерением.
- **Проверка.** Host-тесты на известных ответах независимых реализаций
  (`tests/host/crypto_vectors.h`, сгенерированы `hashlib`/`hmac` и OpenSSL
  через библиотеку `cryptography` инструментом разработчика
  `tests/host/gen_crypto_vectors.py`; сборке и тестам он не нужен) и
  отрицательные случаи (перевёрнутый бит тега, подписи, ключа, сообщения).
- **X.509** (`lib/tls/x509.c`): разбор DER, подписи RSA PKCS#1 v1.5 и ECDSA,
  срок действия по часам гостя, имя по subjectAltName (dNSName, iPAddress,
  wildcard только целой левой меткой), построение пути до якоря из
  хранилища, `basicConstraints`/`keyUsage`, отказ при неизвестном
  критическом расширении. Нет CRL/OCSP, name constraints, политик.

## 7. TLS 1.3 и тестовая PKI

- Клиент RFC 8446: только TLS 1.3, группа X25519, наборы
  `TLS_AES_128_GCM_SHA256` и `TLS_CHACHA20_POLY1305_SHA256`, SNI, ALPN
  `http/1.1`, подписи CertificateVerify RSA-PSS и ECDSA P-256/P-384. Нет PSK,
  0-RTT, клиентских сертификатов, HelloRetryRequest (сервер, который
  попросит другую группу, получает отказ). KeyUpdate поддержан,
  NewSessionTicket игнорируется. `close_notify` различается с обрывом TCP.
- **Отключить проверку сертификата нельзя**: такого параметра нет ни в
  библиотеке, ни в конфигурации.
- Отказы проверки: `cert_untrusted`, `cert_expired`, `cert_name`,
  `cert_bad`, `bad_signature` (класс `tls`), серверу отправляется
  соответствующий alert.
- **Тестовая PKI** `tools/net/pki.py` (только stdlib, детерминированные
  тестовые ключи, кэш в `out/m5-pki/`): профили `ec-leaf` (ECDSA P-256,
  корень → лист), `rsa-chain` (RSA, корень → промежуточный → лист,
  wildcard), `expired`, `wrong-name`, `untrusted`. Сертификаты действуют в
  2025–2030 гг.; OpenSSL проверяет их по настоящему времени, гость — по RTC
  стенда. Корень профиля записывается в хранилище как якорь `tls/anchorN`.

## 8. Provider: протокол и агент

### 8.1 Транспорт

HTTP/1.1 поверх своего TLS (`lib/http/http.c`): инкрементальный разбор
ответа (строка статуса, заголовки, `Content-Length`, `chunked`, тело до
закрытия, промежуточные 1xx), заголовки `Retry-After`, `Connection`,
`request-id`. Keep-alive: соединение живёт между запросами; соединение,
которое сервер закрыл в простое (FIN/RST/`close_notify` до первого байта
ответа), заменяется один раз прозрачно (`reconnect=stale`), не считаясь
попыткой.

Запрос (`provider.c`):

```text
POST /v1/messages HTTP/1.1
Host: <provider.host>[:<port>]
content-type: application/json
accept: text/event-stream
anthropic-version: 2023-06-01
x-api-key: <ключ из хранилища>
content-length: <n>
```

### 8.2 Тело и поток ответа

Тело (`lib/http/messages.c`): `model` (только из конфигурации — в коде нет
идентификатора модели по умолчанию), `max_tokens`, `system`, `tools` (7
инструментов M3 с `input_schema`), `messages` (история с блоками `text`,
`tool_use`, `tool_result`/`is_error`), `stream: true`.

Поток — server-sent events (`lib/http/http.c`, разбор строк CR/LF/CRLF,
многострочные `data:`, комментарии): `message_start`,
`content_block_start` (`text`/`tool_use`), `content_block_delta`
(`text_delta`/`input_json_delta`), `content_block_stop`, `message_delta`
(`stop_reason`, `usage`), `message_stop`, `ping`, `error`. Сборщик
проверяет порядок событий и форму каждого JSON; неизвестное событие,
дельта не того типа или не открытого блока, отсутствие `stop_reason`,
незакрытый блок — `malformed`; ввод инструмента не объект JSON —
`bad_tool`; тело HTTP закончилось без `message_stop` — `malformed`.
Блоки других типов (например, thinking) пропускаются и назад не
отправляются. JSON (`lib/http/json.c`) — валидирующий разбор «на месте»
без дерева, глубина ≤ 32; писатель экранирует управляющие символы и
заменяет неверный UTF-8 на U+FFFD.

### 8.3 Повторы и тайм-ауты

- Тайм-аут одной попытки — ожидание очередных данных `provider.timeout_ms`
  (по умолчанию 20 с; сценарии 3–8 с).
- Повторяются только ошибки, после которых повтор может помочь, — запрос к
  модели не имеет эффектов: сетевые (`link_down`, `dns_timeout`,
  `conn_refused`, `conn_timeout`, `conn_reset`, `unacked_timeout`,
  `peer_closed`), `rate_limit`, `overloaded`, `server_error`,
  `stream_error`, `provider_timeout`, `truncated`. Не повторяются: 400,
  401/403, 404, `malformed`, `malformed_http`, `bad_tool`, ошибки TLS и
  локальные.
- До `provider.attempts` попыток (по умолчанию 3), паузы 0,5 и 1 с;
  `Retry-After` заменяет паузу (не более 10 с). **Действия исполнителя
  никогда не повторяются** — повтор относится только к запросу модели.
- Отрицательный контроль `m5-noretry`: одна попытка, проверки повторов
  проваливаются.

### 8.4 Цикл агента (`agent.ask`)

- Запрос пользователя — UTF-8 в base64url без `=` в значениях `qa`, `qb`,
  `qc` (ключи NCI — только буквы, строка ≤ 256 байт; до 144 байт текста).
- До 10 запросов к модели. Каждый вызов инструмента проверяется по
  таблице (известное имя, только объявленные аргументы, обязательные на
  месте, значения — строки или неотрицательные целые в алфавите NCI) и
  выполняется как обычное действие NCI `<ask>.<n>` через task engine
  (`core_exec`): жизненный цикл, проверка, write-ahead-записи M4 — как для
  запроса оператора, и `action.status` видит их. Ответ исполнителя целиком
  уходит модели как `tool_result` (`is_error`, если не `SUCCEEDED`).
  Отклонённый вызов не выполняется; модели сообщается причина.
- Итог: `SUCCEEDED` — модель ответила и все действия успешны;
  `FAILED code=ACTION_ERROR detail=<код действия> action=<id>` — действие
  провалено (приоритетнее отклонённого вызова: могли быть эффекты);
  `FAILED code=PROVIDER_ERROR detail=bad_tool` — был отклонённый вызов;
  иначе — класс ошибки запроса к модели. Поля: `steps`, `attempts`,
  `retries`, `reconnects`, `actions`, `actions_failed`, `bad_tools`,
  `effects` (выполненные изменяющие операции), `http`, `error_type`.
  Ответ модели (≤ 600 байт, `truncated=yes` при обрезке) — строки
  `ITEM <id> seq=<n> text=<base64url>`.
- Serial-лог получает текст запроса и ответа частями без управляющих
  символов (журнал ядра показывает не-ASCII как `?`).

### 8.5 Конфигурация и ключ

Всё — объекты хранилища M4 (записываются при провижининге диска
`tools/store/nxstore.py`; в стенде — `m5host.Services.provision`):

| Объект | Смысл | По умолчанию |
| --- | --- | --- |
| `cfg/provider.host` | DNS-имя provider (SNI и имя в сертификате) | нет — `LOCAL_ERROR config` |
| `cfg/provider.model` | идентификатор модели | нет — `LOCAL_ERROR config` |
| `cfg/provider.port` | порт | 443 |
| `cfg/provider.key_ref` | имя объекта с ключом | `secret/provider` |
| `cfg/provider.timeout_ms`, `attempts`, `max_tokens` | тайм-аут, попытки (1–5), предел ответа | 20000, 3, 1024 |
| `secret/provider` (вид `KIND_SECRET`) | ключ API (печатаемый ASCII) | нет — `LOCAL_ERROR no_key` |
| `tls/anchor0..3` (вид `KIND_ANCHOR`) | корневые сертификаты DER | нет — `LOCAL_ERROR config` |

Ключ попадает только в заголовок зашифрованного запроса: он не печатается,
не входит в ответы NCI; `provider.status` показывает `key_ref`,
`key=present|missing` и длину. Стенд на каждый запуск создаёт новый
случайный тестовый ключ, провайдер сверяет `x-api-key`, а скрипты
проверяют, что ключ (и его случайная часть) не встречается в serial-логе.

## 9. Классы ошибок и телеметрия

Одно пространство кодов (`lib/include/nanox/nerr.h`), класс определяется
кодом, код сохраняет слой, где обнаружен сбой:

| Класс | Коды | Смысл |
| --- | --- | --- |
| `net` | `link_down`, `arp_timeout`, `dns_timeout`, `dns_notfound`, `dns_bad_reply`, `conn_refused`, `conn_timeout`, `conn_reset`, `unacked_timeout`, `peer_closed`, `net_io` | сеть не доставила |
| `tls` | `cert_untrusted`, `cert_expired`, `cert_name`, `cert_bad`, `bad_signature`, `tls_alert`, `tls_protocol`, `tls_decrypt`, `tls_unsupported` | защищённый канал не установлен или сломан |
| `provider` | `bad_request`, `auth`, `not_found`, `rate_limit`, `overloaded`, `server_error`, `malformed_http`, `malformed`, `stream_error`, `provider_timeout`, `truncated`, `bad_tool`, `no_answer`, `too_large` | provider ответил, но не пригодным ответом модели |
| `action` | код ответа исполнителя (`NOT_FOUND`, `VERIFY_FAILED`, `CONFLICT`, …) | ответ модели в порядке, провалилось выполнение действия |
| `local` | `config`, `no_key`, `entropy`, `resources` | сам гость |

Правила на границе слоёв:

- тайм-аут ожидания с неподтверждёнными данными — `unacked_timeout` (сеть);
  данные подтверждены, а ответа нет — `provider_timeout` (provider);
- при опущенном линке сетевая ошибка становится `link_down`;
- TCP закрыт (FIN/RST) без `close_notify` посреди ответа — `peer_closed` /
  `conn_reset` (сеть); `close_notify` до конца ответа — `truncated`
  (provider);
- HTTP-статус: 401/403 → `auth`, 404 → `not_found`, 429 → `rate_limit`,
  529 → `overloaded`, 5xx → `server_error`, прочие 4xx → `bad_request`;
  событие `error` в потоке — по его `type` (`overloaded_error` →
  `overloaded`, …).

Строки телеметрии в serial-логе (по одной на попытку, действие и запрос):

```text
tel ask=<id> step=<n> attempt=<k> phase=model result=<ok|код> class=<класс> http=<статус> ms=<t> in_tokens= out_tokens= [retry_in=<мс>] [reconnect=stale] [error_type=<тип>]
tel ask=<id> step=<n> phase=action tool=<имя> request=<id.n> result=<STATE> code=<код> class=<ok|action> ms=<t>
tel ask=<id> step=<n> phase=action tool=<имя> request=<id.n> result=bad_tool class=provider reason="..."
tel ask=<id> phase=config result=<код> class=local
tel ask=<id> phase=ask result=<ok|код> class=<класс> detail=<код> steps= attempts= retries= reconnects= actions= actions_failed= bad_tools= effects= ms=
```

`telemetry.status` суммирует исходы по классам с загрузки. Отрицательный
контроль `m5-flattel` делает класс любой ошибки `unclassified`; проверки
`m5-classes` обязаны провалиться.

## 12. Решения M5

1. **Всё сетевое — в пользовательском процессе.** Ядро отдаёт кадры,
   энтропию и время; стек, TLS и provider в `bin/core`. Это держит ядро
   маленьким и делает весь путь host-тестируемым чистым кодом.
2. **virtio-net + slirp.** Не требует root/tap, работает headless; link
   down — через QMP. Цена — поведение slirp (повтор SYN-ACK через ~6 с,
   собственный TCP хоста), учтённое в тайм-аутах.
3. **Опрос вместо прерываний** — как virtio-blk M4; производительность не
   цель этапа.
4. **Свой TLS 1.3 с минимальным набором**: одна группа, два набора, без
   возобновления; этого достаточно для современных серверов и проверяемо
   против OpenSSL. Проверка сертификата не отключается.
5. **Ключ, модель и якоря — в хранилище**, а не в образе: образ
   воспроизводим и не содержит секретов; ключ — объект вида `SECRET`,
   на который ссылается конфигурация.
6. **Потоковый ответ (SSE)** — чтобы различать обрыв потока, ранний
   `close_notify` и ошибку в потоке и иметь тайм-аут между событиями, а не
   на весь ответ.
7. **Инструменты модели = операции NCI** через тот же task engine: у
   действий агента те же проверки, записи и идемпотентность, что у
   оператора; повтор относится к запросу модели, не к действию.
8. **Одно пространство кодов ошибок с классом по коду** — класс не
   теряется при передаче через слои; граничные случаи решаются явными
   правилами (раздел 9).
9. **Отрицательные контроли** для каждого механизма, влияющего на вердикт:
   повторная передача TCP (`m5-noretx`), повтор запроса (`m5-noretry`),
   классификация (`m5-flattel`).

## 13. Что проверено при подготовке этого шага

Эталонная среда та же (Ubuntu 24.04, clang/lld 18.1.3, QEMU 8.2.2, TCG, без
KVM). В рабочем дереве выполнено:

- `make doctor && make && make test` в локальном клоне ревизии `1270d55` —
  код выхода 0: host-тесты C (2356 проверок, UBSan trap; из них сеть,
  криптография, JSON/HTTP/SSE/протокол Messages), 114 Python-тестов (в том
  числе совместимость TLS с OpenSSL и тестовый provider с клиентом
  `http.client`), 54 сценария QEMU с ожидаемыми вердиктами (8 M0, 13 M1, 5
  M2, 7 M3, 9 M4, 12 M5; серия `m4-crash` — 154 пары, 0 нарушений, 1
  перезапуск точки), повторяемость `normal`, `pagefault`, `m2-sched`;
  двенадцать сценариев M5 до этого дважды подряд в рабочем дереве — все с
  ожидаемым вердиктом;
- `make repro-check` — пять артефактов побайтово совпали в трёх сборках;
- `make debug-check` — GDB остановился в `kernel_main`.

Во время подготовки сценарии нашли: потерю SYN-ACK под slirp (тайм-аут

смещение адреса данных `m2-user` из-за таблицы имён ошибок.

## 14. Что не проверено

- **Настоящий provider.** Путь к настоящему API написан (раздел 8), но в
  среде нет `ANTHROPIC_API_KEY` и нет доступа к внешнему API из гостя; ни
  один запрос к настоящему provider не выполнялся. Для такой проверки
  нужно записать в хранилище `cfg/provider.host`, `cfg/provider.model`,
  `secret/provider`, корневой сертификат цепочки provider в `tls/anchor0`,
  и настоящий DNS (`cfg/net.dns=10.0.2.3`, резолвер slirp). Совместимость
  с его TLS (группа X25519, наборы, тип ключа сертификата), форма потока
  (например, дополнительные события) и лимиты не подтверждены.
- **Языковая модель.** Во всех сценариях отвечает сценарная политика
  тестового provider; качество решений модели не оценивалось (критерий 3
  M3 остаётся открытым).
- **TLS**: только против OpenSSL (Python `ssl`) с тестовой PKI; не
  проверялись другие реализации, HelloRetryRequest (не поддержан),
  отзыв сертификатов (не поддержан), постоянное время операций, стойкость к
  атакам (намеренно не испытывалась).
- **Энтропия**: источник — `rng-builtin` QEMU; тесты здоровья проверены на
  векторах, отказ настоящего источника в QEMU не моделировался.
- **Сеть**: только slirp QEMU, IPv4, без фрагментации, без контроля
  перегрузки; потеря — детерминированный слой ядра, а не реальная сеть;
  производительность не измерялась.
- **Пределы**: тело запроса ≤ 48 КиБ (длинная история агента может не
  поместиться — `LOCAL_ERROR resources`), ответ ≤ 8 КиБ текста и 8
  блоков, событие SSE ≤ 8 КиБ, вопрос ≤ 144 байт, ответ в NCI ≤ 600 байт.
- Критерии M2 4–6 и M3 3 этим этапом не закрываются.
- Все результаты получены в QEMU (TCG) и не доказывают работу на реальном
  оборудовании (ARCHITECTURE.md §17).
