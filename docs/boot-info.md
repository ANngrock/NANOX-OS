# Boot info, структура памяти и правила ошибок (M0)

Статус: действует для boot info **1.0**. Нормативный источник раскладки —
`abi/nanox/bootinfo.h`; блок `_Static_assert` в этом заголовке проверяет при
каждой сборке смещения, перечисленные ниже. Если документ и заголовок
расходятся, это ошибка документа.

Связанные файлы:

| Файл | Что определяет |
| --- | --- |
| `abi/nanox/bootinfo.h` | `struct nx_boot_info`, `struct nx_mem_region`, типы регионов, флаги |
| `abi/nanox/manifest.h` | формат `\NANOX\MANIFEST.BIN` |
| `abi/nanox/diag.h` | коды isa-debug-exit и коды ошибок загрузчика |
| `boot/uefi/loader.c` | загрузчик (UEFI-приложение PE/COFF) |
| `boot/uefi/mmap_convert.c` | перевод карты памяти UEFI в карту NANOX |
| `boot/uefi/elf_plan.c` | проверка ELF64 и план загрузки сегментов |
| `kernel/bootinfo_check.c` | проверка boot info на стороне ядра |
| `kernel/arch/x86_64/entry.S`, `kernel/arch/x86_64/kernel.ld` | точка входа и адреса ядра |

## 1. Последовательность загрузчика

`\EFI\BOOT\BOOTX64.EFI` — собственное UEFI-приложение без EDK2/gnu-efi
(минимальные определения UEFI 2.11 — в `boot/uefi/efi.h`).

1. Инициализирует COM1 и печатает `NANOX: loader start`.
2. Отключает UEFI watchdog: на стенде M0 роль watchdog выполняет внешний
   harness (ARCHITECTURE.md §9).
3. Через `EFI_LOADED_IMAGE_PROTOCOL` → `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL`
   открывает том, с которого загружен сам.
4. Читает `\NANOX\MANIFEST.BIN` и проверяет magic, версию, размер, нулевые
   reserved-байты.
5. Читает `\NANOX\KERNEL.ELF`, сравнивает размер и SHA-256 с манифестом.
6. Проверяет ELF64 (`nx_elf_plan`), выделяет весь диапазон ядра по
   фиксированному физическому адресу (`AllocateAddress`, тип памяти
   `0x80000001`), обнуляет его и копирует сегменты `PT_LOAD`.
7. Выделяет стек ядра 64 KiB (тип `0x80000002`).
8. Выделяет блок boot info (тип `0x80000003`) под структуру, командную строку
   и карту памяти.
9. Читает необязательный `\NANOX\CMDLINE.TXT`, находит ACPI RSDP в
   configuration table (сначала ACPI 2.0 GUID, затем 1.0), запрашивает GOP.
10. `GetMemoryMap` → `ExitBootServices`; при неуспехе повторяет только эти два
    вызова (до 4 попыток), как требует UEFI 2.11 §7.4.
11. После `ExitBootServices` переводит карту памяти (без выделения памяти) и
    передаёт управление ядру.

Типы `0x8000000x` лежат в диапазоне, который UEFI резервирует для загрузчиков
ОС; благодаря им регионы ядра, стека и boot info видны в карте памяти самой
прошивки и переносятся в карту NANOX без эвристик.

## 2. Точка входа ядра

Контракт между загрузчиком и `_start` (`kernel/arch/x86_64/entry.S`):

| Состояние | Значение |
| --- | --- |
| Режим CPU | long mode, CPL 0 |
| Трансляция адресов | таблицы страниц UEFI, identity mapping: виртуальный адрес = физическому |
| GDT, IDT | остаются от прошивки; собственные таблицы и обработчики исключений — M1 |
| Прерывания | запрещены (`IF = 0`); загрузчик выполняет `cli` перед переходом |
| `RDI` | физический адрес `struct nx_boot_info` |
| `RSP` | верх региона `NX_MEM_KERNEL_STACK` (`stack_phys_base + stack_size`), выровнен на 4 KiB |
| `RBP` | 0 |
| Boot Services | завершены; вызывать UEFI нельзя (кроме Runtime Services, которые M0 не использует) |

`_start` выравнивает стек и вызывает `kernel_main(const struct nx_boot_info *)`,
которая не возвращается.

## 3. `struct nx_boot_info` 1.0

Все поля little-endian, без неявного выравнивания; размер 192 байта.

| Смещение | Размер | Поле | Смысл |
| ---: | ---: | --- | --- |
| 0 | 8 | `magic` | `0x49425F584F4E414E` (байты `NANOX_BI`) |
| 8 | 2 | `version_major` | `1` |
| 10 | 2 | `version_minor` | `0` |
| 12 | 4 | `size` | число байт структуры, записанных загрузчиком |
| 16 | 8 | `flags` | бит 0 `NX_BI_HAS_ACPI_RSDP`, бит 1 `NX_BI_HAS_FRAMEBUFFER` |
| 24 | 8 | `mmap_phys` | физический адрес массива `nx_mem_region` |
| 32 | 4 | `mmap_count` | число регионов, 1..4096 |
| 36 | 4 | `mmap_entry_size` | `24` |
| 40 | 8 | `kernel_phys_base` | начало диапазона ядра, кратно 4 KiB |
| 48 | 8 | `kernel_phys_size` | размер диапазона ядра, кратно 4 KiB |
| 56 | 8 | `kernel_entry` | `e_entry` ELF |
| 64 | 8 | `stack_phys_base` | начало начального стека, кратно 4 KiB |
| 72 | 8 | `stack_size` | размер стека (65536) |
| 80 | 8 | `cmdline_phys` | адрес командной строки, завершённой NUL |
| 88 | 4 | `cmdline_len` | длина без NUL, не больше 4095 |
| 92 | 4 | `reserved0` | 0 |
| 96 | 8 | `initrd_phys` | зарезервировано под initramfs (M1), в 1.0 равно 0 |
| 104 | 8 | `initrd_size` | зарезервировано под initramfs (M1), в 1.0 равно 0 |
| 112 | 8 | `acpi_rsdp_phys` | RSDP при `NX_BI_HAS_ACPI_RSDP`, иначе 0 |
| 120 | 8 | `fb_phys` | framebuffer при `NX_BI_HAS_FRAMEBUFFER`, иначе 0 |
| 128 | 8 | `fb_size` | байты |
| 136 | 4 | `fb_width` | пиксели |
| 140 | 4 | `fb_height` | пиксели |
| 144 | 4 | `fb_pitch` | байт на строку |
| 148 | 4 | `fb_format` | 1 = RGBX8888, 2 = BGRX8888 |
| 152 | 8 | `uefi_system_table_phys` | справочно; Boot Services уже недоступны |
| 160 | 32 | `kernel_sha256` | SHA-256 файла `KERNEL.ELF`, проверенный загрузчиком |

Framebuffer заполняется только для GOP-форматов RGB/BGR с 8 битами на канал;
`PixelBitMask` и `PixelBltOnly` дают «framebuffer отсутствует» (строка
`NANOX: loader framebuffer unsupported pixel format N`).

### `struct nx_mem_region` (24 байта)

| Смещение | Размер | Поле | Смысл |
| ---: | ---: | --- | --- |
| 0 | 8 | `base` | физический адрес, кратно 4 KiB |
| 8 | 8 | `length` | байты, кратно 4 KiB, больше 0 |
| 16 | 4 | `type` | `enum nx_mem_type` |
| 20 | 4 | `flags` | в 1.0 равно 0 |

Регионы отсортированы по `base`, не пересекаются; соседние регионы одного
типа загрузчик объединяет.

| `type` | Имя | Источник в карте UEFI | Правило использования |
| ---: | --- | --- | --- |
| 1 | `USABLE` | `EfiConventionalMemory` | свободная RAM |
| 2 | `RESERVED` | reserved, unusable, PAL, persistent, unaccepted, неизвестные и OEM-типы | не трогать |
| 3 | `ACPI_RECLAIMABLE` | `EfiACPIReclaimMemory` | освобождается после разбора ACPI |
| 4 | `ACPI_NVS` | `EfiACPIMemoryNVS` | сохранять всегда |
| 5 | `MMIO` | `EfiMemoryMappedIO`, `...IOPortSpace` | устройство, не RAM |
| 6 | `BOOT_RECLAIMABLE` | `EfiLoaderCode/Data`, `EfiBootServicesCode/Data` | освобождается только после перехода ядра на свои таблицы страниц, GDT и IDT (M1): здесь лежат текущие таблицы страниц UEFI |
| 7 | `KERNEL_IMAGE` | загрузчик, тип `0x80000001` | весь диапазон ядра |
| 8 | `KERNEL_STACK` | загрузчик, тип `0x80000002` | начальный стек |
| 9 | `BOOT_INFO` | загрузчик, тип `0x80000003` | boot info, командная строка, карта памяти |
| 10 | `FIRMWARE_RUNTIME` | `EfiRuntimeServicesCode/Data` | сохранять всегда |

## 4. Правила версий

- `version_major` меняется при любом несовместимом изменении. Ядро отвергает
  неизвестный major (`E_VERSION`).
- `version_minor` меняется только при добавлении полей в конец структуры или
  новых битов `flags`. Смещения и смысл существующих полей внутри одного major
  не меняются.
- `size` ≥ 192 и ≤ 4096. Если `version_minor` не больше известного ядру, `size`
  обязан быть в точности `sizeof(struct nx_boot_info)` этого ядра, а
  неизвестные биты `flags` — ошибка (`E_FLAGS`). Если minor новее, лишние байты
  и неизвестные флаги игнорируются.
- Поля, помеченные reserved (`reserved0`, `initrd_*` в 1.0, `nx_mem_region.flags`),
  обязаны быть нулями; их смысл вводится только вместе с повышением minor.
- Любое изменение раскладки сопровождается правкой `_Static_assert` в
  `abi/nanox/bootinfo.h`, этой таблицы и тестов `tests/host/test_bootinfo.c`.

## 5. Проверка boot info ядром

`nx_bootinfo_check()` (`kernel/bootinfo_check.c`) выполняется до любого
использования boot info. Доступ к физической памяти идёт только через
переданную функцию отображения: в ядре это identity mapping, в host-тестах —
фиктивная физическая область. Первая найденная ошибка возвращается как код;
для ошибок карты памяти дополнительно возвращается индекс региона.

| Код | Условие |
| --- | --- |
| `E_NULL` | адрес boot info равен 0, переполняется или не отображается |
| `E_MAGIC` | неверный `magic` |
| `E_VERSION` | `version_major != 1` |
| `E_SIZE` | `size` вне правил раздела 4 |
| `E_FLAGS` | неизвестные биты `flags` при известном minor |
| `E_RESERVED` | ненулевые `reserved0`, `initrd_phys`, `initrd_size` |
| `E_MMAP_ENTRY_SIZE` | `mmap_entry_size != 24` |
| `E_MMAP_COUNT` | `mmap_count` равен 0 или больше 4096 |
| `E_MMAP_PTR` | `mmap_phys` равен 0, не выровнен на 8, переполняется или не отображается |
| `E_MMAP_EMPTY` | регион нулевой длины |
| `E_MMAP_ALIGN` | `base` или `length` не кратны 4 KiB |
| `E_MMAP_OVERFLOW` | `base + length` переполняет 64 бита (конец ровно в 2^64 тоже отвергается) |
| `E_MMAP_TYPE` | неизвестный `type` |
| `E_MMAP_FLAGS` | ненулевые `flags` региона |
| `E_MMAP_ORDER` | регионы не отсортированы |
| `E_MMAP_OVERLAP` | регион начинается внутри предыдущего |
| `E_MMAP_NO_USABLE` | нет ни одного `USABLE` |
| `E_KERNEL_RANGE` | диапазон ядра не выровнен, пуст, переполняется или не покрыт целиком регионами `KERNEL_IMAGE` |
| `E_KERNEL_ENTRY` | `kernel_entry` вне диапазона ядра |
| `E_KERNEL_SELF` | фактический образ ядра (`__kernel_start`..`__kernel_end`) вне диапазона ядра |
| `E_STACK_RANGE` | стек не выровнен, пуст или не покрыт регионами `KERNEL_STACK` |
| `E_BOOTINFO_RANGE` | структура или массив карты памяти не покрыты регионами `BOOT_INFO` |
| `E_CMDLINE` | строка вне `BOOT_INFO`, длиннее 4095, без NUL на позиции `cmdline_len` или с байтами вне 0x20..0x7E |
| `E_RSDP` | флаг и поле не согласованы; RSDP лежит в `USABLE`; неверная сигнатура `RSD PTR `, контрольная сумма первых 20 байт или (для ревизии ≥ 2) расширенная сумма и длина |
| `E_FRAMEBUFFER` | флаг и поля не согласованы; нулевые размеры; `pitch < width*4`; `fb_size < pitch*height`; переполнение; пересечение с RAM-регионами (`USABLE`, `BOOT_RECLAIMABLE`, `KERNEL_*`, `BOOT_INFO`) |

Дополнительно `kernel_main` проверяет, что текущий `RSP` лежит внутри стека из
boot info. Любая ошибка ведёт к panic (раздел 8).

## 6. Структура памяти (стенд M0)

Адреса ядра фиксированы; остальные зависят от прошивки и выбираются
загрузчиком через `AllocateAnyPages`.

| Объект | Адрес | Кто задаёт |
| --- | --- | --- |
| Ядро (VMA = LMA = физический адрес) | `0x200000`, окно допустимых адресов сегментов `0x100000..0x40000000`, не больше 64 MiB | `kernel/arch/x86_64/kernel.ld`, `boot/uefi/elf_plan.h` |
| Точка входа `_start` | `0x200000` (первая функция `.text.entry`) | `kernel.ld` |
| Сегменты ядра | `.text` R+X, `.rodata` R, `.data`/`.bss` R+W, каждый с границы 4 KiB | `kernel.ld` (`PHDRS`) |
| Стек ядра | 64 KiB, любой свободный адрес | загрузчик |
| Блок boot info | структура по смещению 0, командная строка по смещению 256, массив регионов по смещению 4352 | загрузчик (`BI_*_OFFSET`) |
| Таблицы страниц | таблицы UEFI (identity mapping); собственные — M1 | прошивка |

Если диапазон `0x200000..` занят прошивкой, загрузчик завершается ошибкой
`E_KERNEL_ALLOC`; для зафиксированной конфигурации QEMU (docs/m0-bench.md)
диапазон свободен, что подтверждает сценарий `normal`.

Пример карты, переданной ядру в сценарии `normal` (256 MiB RAM, OVMF
2024.02, строки `NANOX: mmap` из `serial.log`):

```text
0x0000000000000000-0x00000000000a0000 usable
0x0000000000100000-0x0000000000200000 usable
0x0000000000200000-0x0000000000203000 kernel_image
0x0000000000203000-0x0000000000800000 usable
0x0000000000800000-0x0000000000808000 acpi_nvs
...
0x000000000e108000-0x000000000e118000 kernel_stack
...
0x000000000e75c000-0x000000000e75f000 boot_info
...
0x000000000f76d000-0x000000000f77f000 acpi_reclaimable
0x00000000e0000000-0x00000000f0000000 reserved
0x00000000ffc00000-0x0000000100000000 mmio
0x000000fd00000000-0x0000010000000000 reserved
```

Регион с `base = 0` может быть `USABLE`; будущий физический allocator не
должен выдавать страницу 0.

## 7. Манифест образа `\NANOX\MANIFEST.BIN` (64 байта)

| Смещение | Размер | Поле | Значение |
| ---: | ---: | --- | --- |
| 0 | 4 | `magic` | `0x464D584E` (`NXMF`) |
| 4 | 2 | `version` | 1 |
| 6 | 2 | `size` | 64 |
| 8 | 8 | `kernel_size` | точный размер `KERNEL.ELF` |
| 16 | 32 | `kernel_sha256` | SHA-256 `KERNEL.ELF` |
| 48 | 16 | `reserved` | нули |

Манифест пишет `tools/image/mkimage.py`. Он обнаруживает отсутствующий,
усечённый или повреждённый файл ядра. Подлинность он не удостоверяет: кто
может переписать `KERNEL.ELF`, может переписать и манифест; подписи в M0 нет.

## 8. Правила ошибок

Все ошибки видны в serial-логе до выхода; строки начинаются с `NANOX: `.
Коды выхода QEMU получаются через `isa-debug-exit` (порт `0xF4`):
статус процесса = `(значение << 1) | 1`.

| Ситуация | Строка serial | Значение порта | Статус QEMU |
| --- | --- | ---: | ---: |
| Тест пройден | `NANOX: TEST PASS` | `0x10` | 33 |
| Тест не пройден | `NANOX: TEST FAIL <причина>` | `0x11` | 35 |
| Panic ядра | `NANOX: PANIC <сообщение>` | `0x12` | 37 |
| Ошибка загрузчика | `NANOX: LOADER ERROR <ИМЯ> (<код>): <подробности> (efi_status=0x...)` | `0x13` | 39 |
| Зависание | — | — | процесс завершает harness по таймауту |
| Сброс/тройная ошибка | — | — | 0 (`-no-reboot`) |

Коды ошибок загрузчика (`abi/nanox/diag.h`):

| Код | Имя | Причина |
| ---: | --- | --- |
| 1 | `E_PROTOCOL` | нет LoadedImage / SimpleFileSystem или не открылся том |
| 2 | `E_MANIFEST_OPEN` | `MANIFEST.BIN` отсутствует или не читается |
| 3 | `E_MANIFEST_INVALID` | неверные размер, magic, версия или reserved |
| 4 | `E_KERNEL_OPEN` | `KERNEL.ELF` отсутствует |
| 5 | `E_KERNEL_READ` | ошибка чтения ядра |
| 6 | `E_KERNEL_SIZE` | размер не совпадает с манифестом |
| 7 | `E_KERNEL_HASH` | SHA-256 не совпадает с манифестом (печатаются оба хеша) |
| 8 | `E_ELF_INVALID` | ELF отвергнут (`nx_elf_strerror`: ident, тип, program headers, границы и порядок сегментов, окно адресов, точка входа вне исполняемого сегмента, размер) |
| 9 | `E_KERNEL_ALLOC` | фиксированный физический диапазон ядра занят |
| 10 | `E_CMDLINE` | `CMDLINE.TXT` не читается, длиннее 4095 байт или содержит непечатаемые байты |
| 11 | `E_MEMMAP` | карта памяти недоступна, неизвестная версия дескриптора, ошибки перевода (выравнивание, переполнение, пересечения, ёмкость) |
| 12 | `E_EXIT_BOOT_SERVICES` | `ExitBootServices` не удался за 4 попытки |
| 13 | `E_OUT_OF_MEMORY` | не выделены pool/страницы |

Поведение вне QEMU (устройства `isa-debug-exit` нет): до `ExitBootServices`
загрузчик возвращает прошивке `EFI_LOAD_ERROR`; после — останавливает CPU
(`cli; hlt`). Ядро после записи в порт всегда останавливает CPU.

Путь panic: `nx_panic()` запрещает прерывания, печатает
`NANOX: PANIC <сообщение>`, пишет `0x12` в порт `0xF4` и останавливает CPU.
Исключения CPU в M0 обрабатывает ещё таблица IDT прошивки; собственные
обработчики с диагностикой — критерий M1. Harness в таком случае фиксирует
таймаут или неожиданный статус выхода.

## 9. Ограничения M0

- Собственные таблицы страниц, GDT, IDT и обработчики исключений не созданы
  (M1). Ядро работает на identity mapping прошивки.
- initramfs не загружается; поля `initrd_*` зарезервированы.
- Ядро не проверяет NX-атрибуты страниц; работоспособность перехода в регион
  типа `0x80000001` подтверждена только для зафиксированной сборки OVMF.
- Framebuffer-путь проверен в одном сценарии (`framebuffer`, устройство
  `VGA`, формат BGRX8888); формат RGBX8888 на стенде не встречался и
  проверен только host-тестом валидатора.
- Диагностика загрузчика идёт только в COM1, не в `ConOut`.
