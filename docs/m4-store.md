# M4: постоянное состояние — virtio-blk, хранилище nxstore, протокол durability

Документ фиксирует решения этапа M4 (ARCHITECTURE.md §15) и то, чем
подтверждён каждый критерий. Стенд, harness и коды выхода —
[m0-bench.md](m0-bench.md); задачи, системные вызовы 1–13 —
[m2-kernel.md](m2-kernel.md); NCI, исполнитель `bin/core` и task engine —
[m3-core.md](m3-core.md). ARCHITECTURE.md §10 задаёт модель («неизменяемые
блоки содержимого, версии метаданных, корни состояний и журнал фиксации»,
путь — индекс, а не идентичность) и список обязательных проверок; формат
диска, протокол фиксации, правила восстановления, политика хранения,
раскладка системных вызовов 22–25 и способ искусственного сбоя там не
заданы — это решения M4 (раздел 13).

**Готовность M4** («после искусственного сбоя наблюдается допустимое целое
состояние; изменения не объявляются сохранёнными до завершения обещанного
протокола durability») **подтверждена в объёме модели сбоя раздела 9**: в
QEMU (TCG) серия `m4-crash` останавливает рабочую нагрузку перед каждой из
60 её операций записи и flush (153 запуска с разными политиками потери
незафиксированных записей); после каждой остановки загрузка проверки
находит поколение не старше последнего объявленного сохранённым и не новее
последнего начатого, с содержимым ровно этого поколения по модели, и это
подтверждают и сам исполнитель, и независимый host-читатель диска.
Отрицательный контроль (flush, который ничего не делает) нарушения
обнаруживает. Искусственный сбой — остановка машины гостем в заданной точке
плюс эмуляция энергозависимого кэша записи в ядре; настоящее отключение
питания, реальное оборудование и собственный кэш QEMU/хоста не проверялись
(раздел 15).

Драйвер находится в ядре — это допустимое ARCHITECTURE.md §5.1 раннее
исключение «несколько встроенных драйверов»; вынос драйверов в отдельные
процессы не делался. Логика хранилища в ядро не входит: её исполняет
`bin/core` через системные вызовы блочного устройства. Модель DMA
(ARCHITECTURE.md §5.1): устройство читает и пишет только страницы драйвера
(очередь, заголовок запроса, 8 bounce-страниц), виртуальному устройству QEMU
доверяем, IOMMU нет.

## 3. virtio-blk

- **Транспорт**: virtio 1.x «modern» через PCI capabilities (VIRTIO v1.3
  §4.1): common, notify, device config; обязателен `VIRTIO_F_VERSION_1`,
  принимаются `VIRTIO_BLK_F_RO`, `F_BLK_SIZE`, `F_FLUSH`. BAR назначает
  прошивка (OVMF); ядро включает Memory Space и Bus Master и отображает
  регионы некэшируемыми (`nx_vmm_map_mmio`).
- **Очередь**: одна (queue 0), размер 16, один запрос в полёте: заголовок,
  до 8 страниц данных, байт состояния. Завершение — опросом used ring внутри
  системного вызова (прерывания запрещены на всё время вызова, у ядра нет
  маршрутизации прерываний устройств); предел опроса ~4·10⁸ итераций, затем
  `NX_VBLK_E_TIMEOUT` → `NX_EIO`.
- **Выбор диска данных**: по серийному номеру `nanox-data` (запрос
  `VIRTIO_BLK_T_GET_ID`); загрузочный диск стенда подключён `readonly=on` и
  виден как `ro=yes`.
- **Системные вызовы** (блок = 4096 байт = 8 секторов):

| № | Вызов | Аргументы → результат | Права |
| ---: | --- | --- | --- |
| 22 | `BLK_INFO` | `(h, info*)` → 0: блоки, размер блока, флаги (`READ_ONLY`, `FLUSH`, `TEST_CACHE`), счётчики, серийный номер | `READ` |
| 23 | `BLK_READ` | `(h, блок, n ≤ 8, buf)` → n | `READ` |
| 24 | `BLK_WRITE` | `(h, блок, n ≤ 8, buf)` → n; запись может оставаться энергозависимой до `BLK_FLUSH` | `WRITE` |
| 25 | `BLK_FLUSH` | `(h)` → 0, когда каждая завершённая запись устойчива | `WRITE` |

  Новая ошибка `NX_EIO` (13): устройство сообщило ошибку или не ответило.
  Выход за ёмкость — `NX_EINVAL` до обращения к устройству. Handle диска
  ядро выдаёт только `bin/core` и только в режимах `m4-*`; в режимах M3
  `a3 = 0` и хранилища нет.

## 4. Формат nxstore v1

Блоки по 4096 байт, little endian. Контрольная сумма — CRC-32 IEEE
(полином `0xEDB88320`, как `zlib.crc32`); она обнаруживает оборванные и
повреждённые блоки, но не защищает от намеренной подделки (ARCHITECTURE.md
§10: хеш сам по себе не удостоверяет автора).

| Блоки | Содержимое |
| --- | --- |
| 0, 1 | слоты суперблока A и B (`struct st_super`) |
| 2 … | корни поколений (`struct st_root`, по одному блоку) и экстенты данных объектов |

**Суперблок** (64 байта полей, затем нули, CRC-32 в последних 4 байтах блока
по байтам `[0, 4092)`): `magic "NXSTSUP1"`, `version = 1`,
`block_size = 4096`, `block_count`, `store_id`, `gen`, `root_blk`,
`root_crc` (CRC корня), `retain`, `boot_id` фиксации.

**Корень поколения** (один блок, CRC-32 в конце):

| Смещение | Поле |
| ---: | --- |
| 0 | `magic "NXSTROOT"`, `gen`, `parent_gen`, `store_id`, `next_oid`, `boot_id` |
| 48 | `nobj`, `nhist`, `npin`, `nlog`, `retain`, `flags`; 72: `label[16]` |
| 128 | `hist[8]`: ссылки `{gen, blk, crc}` на сохраняемые прежние поколения, новые первыми |
| 256 | `pin[4]`: `{name[16], gen, blk, crc}` — закреплённые поколения |
| 384 | `log[16]`: журнал фиксаций `{gen, boot_id, label[16]}`, `log[0]` — эта фиксация |
| 896 | `obj[49]` по 64 байта: `oid`, `mod_gen`, `version`, `blk`, `len`, `crc`, `kind`, `nblk`, `name[28]` |
| 4092 | CRC-32 байтов `[0, 4092)` |

- **Объект**: постоянная идентичность — `oid` (выдаётся из `next_oid`, не
  переиспользуется); путь (`name`, `[A-Za-z0-9._/-]{1,27}`) — индекс к нему
  в данном корне (ARCHITECTURE.md §10). `version` — 1 при создании, +1 при
  каждом изменении; `mod_gen` — поколение последнего изменения. Содержимое —
  один непрерывный экстент из `nblk = ceil(len/4096)` блоков (0–8 блоков,
  до 32 КиБ), хвост блока — нули, CRC — по `len` байтам. Неизменённые
  объекты разделяют экстенты между поколениями (copy-on-write).
- **Структурные правила** (проверяют и монтирование, и host-читатель):
  имена уникальны и завершены нулём, `oid` уникальны и меньше `next_oid`,
  `mod_gen ≤ gen`, экстенты лежат в `[2, block_count)` и не пересекаются
  внутри корня, `hist` строго убывает и меньше `gen`, закреплённое
  поколение меньше `gen`, `log[0].gen = gen`, `2 ≤ retain ≤ 9`.
- **Пустое хранилище** (цель сборки `out/data.img`, `nxstore.py format`):
  1 МиБ, 256 блоков, `retain = 4`, поколение 1 без объектов в слоте A,
  метка `format`, слот B — нули. Файл побайтово детерминирован и входит в
  `make repro-check`.

## 5. Протокол durability (фиксация)

Транзакция (`st_begin` … `st_commit`) собирает новый корень в памяти;
`st_put` сразу пишет данные объекта в свободные блоки (ни одно
сохраняемое поколение на них не ссылается, поэтому запись ничего не
меняет). Фиксация `st_commit`:

1. записать корень нового поколения `G = max_gen + 1` в свободный блок;
2. **flush** — данные и корень устойчивы раньше, чем на них сошлётся
   суперблок;
3. записать суперблок в слот, **не** содержащий текущее поколение;
4. **flush** — только теперь поколение `G` устойчиво; `st_commit` возвращает
   `ST_OK`, исполнитель печатает `store saved gen=G` и отвечает `saved=yes`.

Инварианты (`lib/store.c`, проверяются host-симуляцией):

- I1 — фиксация пишет только блоки, на которые не ссылается ни одно
  сохраняемое поколение текущего устойчивого корня и которые ещё не заняты
  этой транзакцией;
- I2 — корень и все его экстенты сброшены до записи суперблока;
- I3 — слот текущего поколения фиксацией не перезаписывается;
- I4 — «сохранено» объявляется только после flush шага 4;
- I5 — монтирование ничего не пишет и принимает поколение, только если
  проверены его суперблок, корень и каждый экстент;
- I6 — поколение во втором слоте входит в сохраняемые текущим (`retain ≥ 2`),
  поэтому откат к нему никогда не находит переиспользованных блоков.

Ошибка устройства до шага 3 — транзакция отброшена, ничего не изменилось
(`ST_E_IO`). Ошибка на шагах 3–4 — исход неизвестен (`ST_E_UNKNOWN`):
хранилище размонтирует себя, исполнитель монтирует его заново и отвечает
`OUTCOME_UNKNOWN code=STORE_ERROR effects=unknown`.

Host-симуляция показала, что каждый из механизмов I2 (барьер) и I5
(проверка при монтировании) в одиночку сохраняет согласованность при
модели устройства раздела 9, а без обоих она нарушается (раздел 10).
Оставлены оба.

## 6. Восстановление (монтирование)

1. Прочитать оба слота: нет магии — `empty`; CRC не сошлась (в том числе
   оборванная запись) — `bad_crc`; неверные версия, размер блока или число
   блоков — `bad_header`; иначе кандидат.
2. Кандидаты — от большего поколения к меньшему (при равенстве слот A). Для
   кандидата прочитать корень: CRC корня совпадает с его полем и с `root_crc`
   суперблока, поколение и `store_id` те же, структура корректна; затем
   прочитать каждый экстент объектов и сверить CRC. Первый прошедший
   кандидат монтируется, отвергнутый — `bad_root` или `bad_data`.
3. Нет ни одного — `ST_E_NOROOT`: хранилище не монтируется, автоматического
   форматирования нет; исполнитель продолжает обслуживать NCI без
   хранилища (ARCHITECTURE.md §5.4), операции хранилища отвечают
   `NO_STORE effects=none`.
4. `max_gen` — наибольшее поколение среди суперблоков с верной CRC; следующая
   фиксация получает `max_gen + 1`, поэтому номер не повторяется даже после
   отката от повреждённого поколения.

Монтирование только читает (сбой во время него безопасен). Если
смонтировано не самое новое поколение из кандидатов, отчёт содержит
`fallback=1`, `rejected_gen` и причину: так повреждение носителя
отличается от обычного сбоя (оборванный суперблок последней фиксации —
это `bad_crc` без `fallback`).

## 7. Политика хранения и удаления

- **Окно**: корень поколения `G` сохраняет `G` и `retain − 1` предыдущих
  (`hist`; на диске стенда `retain = 4`). Содержимое поколения вне окна и
  без закрепления освобождается.
- **Ссылки на поколения (закрепления)**: до 4 именованных закреплений
  (`history.pin name= gen=`); закрепить можно только поколение, которое ещё
  сохраняется. Закреплённое поколение сохраняется вне окна до
  `history.unpin`. Это место для будущих ссылок системных поколений M6
  (снимок данных для отката, ARCHITECTURE.md §9).
- **Журнал фиксаций**: последние 16 фиксаций (`gen`, `boot_id`, метка)
  остаются в каждом корне и после освобождения содержимого; `history.list`
  отмечает их `content=kept|pruned`.
- **Удалённые объекты** исчезают из нового поколения сразу; их блоки
  освобождаются, когда на них не ссылается ни одно сохраняемое поколение.
- **Когда блок снова можно занять**: только после того, как устойчива
  фиксация, отпустившая последнюю ссылку на него (занятость пересчитывается
  по сохраняемым корням после каждой фиксации; постоянной карты свободных
  блоков нет, поэтому «сборка мусора» не пишет на диск и не может его
  испортить).
- **`store.prune`**: следующая фиксация сохраняет только себя и родителя
  (минимум, нужный для I6); закрепления не затрагиваются.
- **Резерв**: обычная запись оставляет свободными 10 блоков; транзакции,
  освобождающие место (удаление, открепление, prune), могут их занять —
  своей записью task engine и корнем, и так же следующая, которая отпустит
  родительское поколение. Поэтому заполненное хранилище всегда можно
  освободить (`m4-full`, `test_full`).
- **Старое содержимое на диске** не затирается: освобождённые блоки
  содержат прежние данные до перезаписи (конфиденциальность — не цель M4).

## 8. Состояние исполнителя (`bin/core`) в хранилище

| Объект | Вид | Содержимое |
| --- | --- | --- |
| `cfg/<key>` | 1 | значение конфигурации (символы значения NCI, до 64) |
| `blob/<name>` | 2 | тестовые данные размера 1–32768 байт, байт `i` = `nx_m4_blob_byte(hash(name), size, i)` |
| `core/tasks` | 3 | заголовок `NXTASKS1` и до 32 записей task engine по 320 байт: `id`, `op`, состояние (`ACT_*`), флаги, отпечаток запроса, `boot_id`, первая строка ответа |

- **Изменение хранилища и его запись task engine — одна транзакция**: после
  сбоя есть либо и изменение, и запись `SUCCEEDED`, либо ни того, ни другого.
  Ответ содержит `gen=` и `saved=yes`; фаза `VERIFYING` перечитывает объект
  через устройство и находит свою запись (`checks=committed,readback,record`).
- **Действия с эффектом вне хранилища** (`task.spawn`, `task.terminate`)
  атомарно с записью не делаются: до системного вызова фиксируется запись
  `RUNNING` (метка `<id>:s`), после — итоговая (`<id>:d`), и только тогда в
  ответ добавляется `saved=yes` (иначе `saved=no`). Запись, найденная при
  старте в неитоговом состоянии, становится `OUTCOME_UNKNOWN`
  (`code=INTERRUPTED detail=boot_<id> effects=unknown`) — это фиксируется
  («recover») — ARCHITECTURE.md §7: потеря ответа не доказывает неисполнение.
- **Дедупликация через перезагрузку**: восстановленные записи попадают в
  task engine (`eng_restore`); повтор запроса прежней загрузки с тем же `id`
  и отпечатком отвечается из записи (`replayed=1`) без исполнения, с другим
  отпечатком — `REJECTED ID_REUSED`. `action.status` добавляет `boot=`,
  `persisted=yes|no`, `restored=yes|no`. Поэтому на стороне host `id`
  запросов с хранилищем должны быть уникальны между загрузками (сценарии M4
  используют префикс загрузки).
- Операции без эффектов (чтения) и неудавшиеся операции хранилища (без
  эффекта) в хранилище не записываются.
- В хранилище лежат записи, которые остаются в памяти task engine (32
  записи на все запросы). При вытеснении task engine сначала отдаёт
  завершённые записи, которых нет в хранилище, и только затем самые старые
  сохранённые; вытесненная сохранённая запись исчезает из `core/tasks` при
  следующей фиксации (в прежних поколениях она остаётся, пока они
  сохраняются).

**Операции NCI** (добавлены в `ops=` у `system.describe`; без хранилища —
`FAILED NO_STORE effects=none`):

| Операция | Аргументы | Эффект / ответ |
| --- | --- | --- |
| `store.status` | — | `state=mounted|unmountable|absent`, `slots=`, `gen`, `label`, `fallback`, `rejected_gen`, `free`, `retain`, `objects`, `pins`, `history`, `restored_tasks`, `outcome_unknown` |
| `store.check` | — | полная проверка (`st_check`): `SUCCEEDED verify=ok` или `VERIFY_FAILED` |
| `store.prune` | — | фиксация с минимальной историей |
| `config.set` / `config.delete` | `key` (`[a-z0-9._-]{1,23}`), `value` | фиксация; `version`, `gen`, `saved=yes` |
| `config.get` | `key`, необязательно `gen` | значение из текущего или сохраняемого поколения; `PRUNED`, `NOT_FOUND` |
| `config.list` | — | `ITEM` на каждый ключ |
| `blob.put` / `blob.delete` / `blob.check` | `name`, `size` / `name` / `name`, `gen` | тестовые данные (заполнение диска, серии сбоев) |
| `history.list` | — | `ITEM` на запись журнала: `gen`, `boot`, `label`, `content`, `pin` |
| `history.pin` / `history.unpin` | `name`, `gen` / `name` | фиксация закрепления |

Коды ошибок (дополнение к m3-core.md §4): `NO_STORE`, `NO_SPACE` (нет
экстента, таблица объектов или закреплений заполнена), `PRUNED`,
`STORE_ERROR`.

## 9. Тестовый слой сбоев (ядро)

Параметры командной строки любого режима `m4-*`:

| Параметр | Смысл |
| --- | --- |
| `nanox.m4.cache=volatile` | эмулировать энергозависимый кэш записи: `BLK_WRITE` оставляет блоки в памяти ядра (чтения их видят), `BLK_FLUSH` пишет их на устройство по порядку и делает `VIRTIO_BLK_T_FLUSH`; переполненный кэш (128 блоков) пишет старейший блок раньше |
| `nanox.m4.crash=K` | перед операцией записи/flush номер `K` ядро «теряет питание»: применяет политику, печатает `NANOX: CRASH POINT io=K …` и выходит со статусом 43 |
| `nanox.m4.lose=all` | из незафиксированных записей не доходит ни одна (потеря питания с кэшем) |
| `nanox.m4.lose=none` | доходят все по порядку (сбой процесса, устройство без кэша) |
| `nanox.m4.lose=torn` | доходят все, кроме последней, от которой только первая половина блока (секторы 0–3) |
| `nanox.m4.lose=reorder` | доходит только последняя (устройство записало не по порядку) |
| `nanox.m4.flush=noop` | отрицательный контроль: flush сообщает успех и ничего не пишет |

Каждая операция записи и flush нумеруется и печатается
(`NANOX: m4 io <n> write blk=… n=… pending=<незафиксированных до неё>`).
QEMU при остановке завершается штатно (`isa-debug-exit`): всё, что гость
отправил устройству, уже в файле; потеря данных моделируется только кэшем
ядра. Это модель сбоя, а не настоящее отключение питания (раздел 15).

## 10. Проверка устойчивости к сбоям

**Host-симуляция** (`tests/host/test_store.c`, `crash_sim`): устройство, у
которого запись лежит в энергозависимом кэше до flush. Рабочая нагрузка из
11 транзакций (объекты 0–8 блоков, перезапись, удаление, закрепление,
открепление, prune, переиспользование освобождённых блоков на диске из 64
блоков) останавливается перед каждой из её 58 операций и после последней
(59 точек). Для каждой точки монтируются все допустимые исходы: при ≤ 6
незафиксированных блоках — все подмножества, иначе префиксы, суффиксы,
одиночные, «все кроме одного» и 16 псевдослучайных; плюс для каждой
незафиксированной записи — «предыдущие дошли, эта наполовину» (обе
половины). Всего 445 монтирований. Для каждого: монтирование успешно,
поколение между последним объявленным сохранённым и начатым, содержимое
совпадает с моделью этого поколения, каждое сохраняемое прежнее поколение и
закрепление — со своей моделью, `st_check` без замечаний. Результат: 0
нарушений.

Отрицательные контроли симуляции (флаги `ST_TEST_*`, в рабочем коде 0) —
каждый обязан дать нарушение, и даёт:

| Поломка | Найденное нарушение |
| --- | --- |
| «сохранено» до flush суперблока | поколение меньше объявленного сохранённым |
| flush отсутствует совсем | то же |
| нет барьера и нет проверки при монтировании | смонтирован мусор вместо корня |
| один слот суперблока | оборванный суперблок: хранилище не монтируется |
| занимаются блоки сохраняемых поколений | текущее поколение испорчено, не монтируется |

Без одного барьера или без одной проверки при монтировании нарушений нет
(каждый механизм достаточен в этой модели) — это записано как результат, а
не как повод убрать один из них.

**Серия сбоев в QEMU** (`m4-crash`, `harness.py` + `storecheck.py`):

1. Эталонный прогон `m4-work` с эмулируемым кэшем: встроенная нагрузка
   `bin/core` из 9 запросов — `config.set`, `blob.put` (3 блока),
   `history.pin`, `task.spawn` и `task.terminate` (write-ahead и итоговые
   записи), `config.set`, `blob.delete` (данные остаются в закреплённом
   поколении), `history.unpin`, `config.set` (занимает освобождённые блоки) —
   11 фиксаций, 60 операций ввода-вывода; затем загрузка проверки
   (`m4-check`) того же диска.
2. Для каждой операции `K = 1…60` и каждой политики, меняющей исход при
   данном числе незафиксированных записей (0 → `all`; 1 → `all`, `none`,
   `torn`; ≥ 2 → также `reorder`), — 153 пары загрузок: загрузка сбоя со
   свежей копией диска, затем загрузка проверки на том же диске.
3. Вердикт точки: загрузка сбоя остановилась именно на `K` (статус 43), и
   операции `1…K−1` совпадают с эталоном построчно (детерминизм);
   исполнитель смонтировал поколение не старше последнего `store saved` и не
   новее последнего `store commit begin` (иначе нарушение `saved_lost`);
   состояние после восстановления (`m4 state …`) и состояние, прочитанное
   host-реализацией с диска, совпадают с моделью этого поколения
   (конфигурация, blob, закрепления, записи task engine с
   `RUNNING → OUTCOME_UNKNOWN`); обе проверки целостности без замечаний.
   Модель строится на host из запросов нагрузки и меток фиксаций эталона
   (`storecheck.model_states`). Эталонный прогон с загрузкой проверки
   оценивается так же, как точка «после последней операции» (`K = 61`).
4. Пары выполняются параллельно (`NANOX_JOBS`, по умолчанию 3 при 4 CPU).
   Точка, загрузка которой не дошла до контроллера M4 (например, самопроверка
   таймера M1 под нагрузкой хоста), считается ошибкой стенда, а не
   нарушением, и перезапускается один раз; перезапуски записываются в
   `record.json` (`summary.retried`).

**Отрицательный контроль** `m4-crash-noflush`: та же нагрузка с
`nanox.m4.flush=noop`; остановка сразу после каждого `store saved` с
политикой `all` обязана потерять объявленное сохранённым (`saved_lost`).

## 13. Решения M4

1. Драйвер virtio-blk — в ядре (раннее исключение §5.1), хранилище — код
   пользовательского процесса `bin/core` (`lib/store.c`); ядро не разбирает
   формат.
2. Транспорт virtio 1.x по PCI capabilities, опрос вместо прерываний, одна
   очередь из 16 дескрипторов, один запрос в полёте.
3. Диск данных определяется серийным номером `nanox-data`, а не адресом PCI.
4. Блок 4096 байт; запрос до 8 блоков; flush — отдельный вызов.
5. Формат — теневые страницы (copy-on-write) с двумя слотами суперблока и
   одним корнем на поколение, а не журнал упреждающей записи: восстановление
   сводится к выбору корня и не требует воспроизведения журнала; «журнал
   фиксации» ARCHITECTURE.md §10 — это `log[]` в корне.
6. Протокол из двух flush; «сохранено» — только после второго.
7. Монтирование проверяет всё текущее поколение (корень и все экстенты) —
   время монтирования пропорционально объёму текущих данных (до 49 × 32 КиБ).
8. Политика хранения: окно `retain = 4` (параметр форматирования, 2–9), до 4
   закреплений, журнал на 16 фиксаций, минимум истории 2, без постоянной
   карты свободных блоков; резерв 10 блоков для освобождающих транзакций.
9. Исполнитель хранит конфигурацию, тестовые blob и записи task engine;
   изменение хранилища и запись — одна транзакция, действия с эффектом в
   ядре — write-ahead и итоговая запись, прерванные — `OUTCOME_UNKNOWN`.
10. Идентификаторы запросов NCI с хранилищем — ключи дедупликации между
    загрузками.
11. Модель сбоя в QEMU — остановка гостем перед операцией `K` плюс
    эмулируемый кэш ядра с четырьмя политиками; полный перебор подмножеств —
    в host-симуляции.
12. Диск данных стенда — 1 МиБ, создаётся host-реализацией формата
    (независимой от `lib/store.c`), каждый сценарий работает на копии.
13. Серия сбоев запускает пары загрузок параллельно; точка, упавшая до
    контроллера M4, перезапускается один раз (записывается).

## 15. Что не проверено

- **Настоящее отключение питания и реальное оборудование.** Сбой — это
  штатный выход QEMU по команде гостя; потеря незафиксированных данных
  моделируется кэшем ядра, а не кэшем QEMU, файловой системы хоста или
  диска. Устойчивость файла образа на хосте после `fdatasync` QEMU не
  проверялась.
- **Оборванная запись в QEMU** — только одна форма: последняя
  незафиксированная запись дошла первой половиной блока (секторы 0–3).
  Host-симуляция перебирает обе половины каждой незафиксированной записи, но
  не произвольные подмножества секторов.
- **Переупорядочивание в QEMU** — политиками `none` и `reorder`; все
  подмножества незафиксированных записей перебирает только host-симуляция
  (при ≤ 6 блоках полностью, иначе выборочно).
- **Ошибки ввода-вывода устройства** в QEMU не внедрялись; путь
  `ST_E_IO`/`ST_E_UNKNOWN` проверен только host-тестами.
- **Серия сбоев покрывает встроенную нагрузку**, а не операции, приходящие
  через bridge; сбой во время фиксации «recover» при старте не перебирался.
- **Повреждения носителя**: проверены инвертированный байт корня,
  суперблока, экстента данных и обоих суперблоков; произвольные повреждения
  не перебирались. CRC-32 обнаруживает случайные повреждения с
  вероятностью пропуска 2⁻³² на проверку и не защищает от намеренной
  подделки. Повреждённое поколение, объявленное сохранённым, теряется
  (откат к предыдущему сообщается, но данные не восстанавливаются).
- **Пределы**: 49 объектов в корне, 32 КиБ на объект, 32 записи task engine,
  до 128 МиБ устройства; заполнение проверено только на диске 1 МиБ.
  Производительность (время фиксации, монтирования) не измерялась.
- **Модель ИИ** операциями хранилища не пользуется: инструменты адаптера
  (`toolspec.py`) не расширялись; сценарии M4 работают через host-скрипты.
- Самопроверка таймера M1 чувствительна к нагрузке хоста при параллельных
  гостях TCG; серия сбоев перезапускает такие точки один раз.
- Критерии M2 4–6 и M3 3 этим этапом не закрываются.
- Все результаты получены в QEMU (TCG) и не доказывают работу на реальном
  оборудовании (ARCHITECTURE.md §17).
