# M3: первый замкнутый цикл ИИ — NCI, исполнитель, host bridge

Документ фиксирует решения этапа M3 (ARCHITECTURE.md §15) и то, чем
подтверждён каждый критерий. Стенд, harness и коды выхода —
[m0-bench.md](m0-bench.md); задачи, планировщик, handles и системные вызовы
1–13 — [m2-kernel.md](m2-kernel.md). Формат строк NCI, набор операций,
коды ошибок, раскладка системных вызовов 14–21, модель ссылок на объекты,
протокол восстановления после потери ответа и формат трассы в
ARCHITECTURE.md не заданы; это решения M3 (раздел 10).

С M4 исполнитель получает четвёртый аргумент — handle диска данных — и
хранит конфигурацию, историю и свои записи task engine в постоянном
хранилище; в режимах M3 (`a3 = 0`) поведение прежнее. Новые операции NCI,
поля `action.status` и дедупликация между загрузками —
[m4-store.md §8](m4-store.md#8-состояние-исполнителя-bincore-в-хранилище).

Готовность M3 («действия реально выполняются внутри собственного ядра …
демонстрация ИИ требует подключения настоящего provider») **не
достигнута**: действия действительно выполняет ядро NANOX, но настоящая
модель к bridge не подключалась — в среде подготовки нет учётных данных
provider. Цикл проверен с мок-моделью, что ARCHITECTURE.md допускает только
для теста протокола.

## 2. Граница guest/host

```text
 host (Linux, Python, tools/bridge/)            │  guest (NANOX в QEMU)
                                                │
 запрос пользователя                            │
   → адаптер модели (mock | unavailable |       │
     anthropic): выбирает инструмент            │
   → agent.py: проверяет вызов по toolspec,     │
     пишет трассу, шлёт строку NCI ─────────────┼─► COM2 (0x2F8) ─► ядро: объект channel
                                                │     └─► bin/core (ring 3, handle channel
                                                │         + handle Sovereign от ядра)
                                                │           task engine: OBSERVING → PLANNED
                                                │           → RUNNING (syscall) → VERIFYING
                                                │           → SUCCEEDED | FAILED
   ◄── RES/ITEM/END ◄───────────────────────────┼─── ответ, verify=, checks=
   → host-проверки, трасса, следующий шаг       │
   → session.close host_checks=ok|fail          │  → exit code bin/core → вердикт ядра
```

- **Канал.** Второй последовательный порт QEMU (COM2, I/O `0x2F8`), на
  стороне host — unix-сокет, который слушает harness; QEMU подключается к
  нему клиентом (`-chardev socket,id=nxbridge,path=…,server=off -serial
  chardev:nxbridge`). Это единственное отличие конфигурации сценариев M3 от
  канонической (как `-device VGA` у сценария `framebuffer`). Прошивка OVMF
  тоже пишет в COM2 свой вывод до загрузки; host пропускает всё до строки
  `HELLO`.
- **Что делает host:** хранит разговор с моделью, вызывает модель,
  проверяет, что выбранный инструмент есть в таблице `toolspec.TOOLS` и
  аргументы полны, переводит его в строку NCI, пишет трассу, выполняет
  независимые host-проверки итогового состояния через те же операции NCI.
  Host не выполняет действий над ОС и не имеет другого доступа к гостю,
  кроме строк NCI.
- **Что делает guest:** ядро выдаёт handle канала (права `READ|WRITE`) и
  handle Sovereign (право `SOVEREIGN`) только `bin/core`. Исполнитель сам
  разбирает запрос, проверяет ссылки и предусловия, выбирает системный
  вызов, выполняет его и проверяет конечное состояние по данным ядра.
  Результат действия определяет гость, а не ответ модели и не host.
- **Доверие.** Ядро не доверяет содержимому канала: строки разбирает
  пользовательский процесс, ядро видит только системные вызовы `bin/core`
  с обычной проверкой handle и прав (m2-kernel.md §6). Host доверяет гостю в
  том, что сообщает гость; его собственные проверки — повторное чтение
  состояния через NCI, то есть сверка с тем же источником, а не
  независимое измерение.
- **Вердикт.** В конце host сообщает итог своих проверок
  (`session.close host_checks=ok|fail reason=<код>`). Это влияет только на
  код выхода `bin/core` и тем самым на вердикт тестового прогона, а не на
  состояние ОС.

Это «явно обозначенный host bridge» из ARCHITECTURE.md §8.3 и §14:
демонстрирует собственную ОС и реальное управление ею, но не автономный
сетевой клиент и не локальную модель (M5, M8).

## 4. NCI v1: формат строк

Одна строка — одно сообщение, ASCII, `\n` в конце (`\r` перед ним
игнорируется). Лексемы разделены пробелами.

```text
HELLO nci=1 core=<ref> boot=<16 hex> dedup=on|off     гость, один раз при старте
REQ <id> <operation> [<key>=<value> ...]              host → гость, до 256 байт
RES <id> <STATE> [<key>=<value> ...]                  гость → host
ITEM <id> [<key>=<value> ...]                         ноль или больше
END <id>
```

- `id` — `[A-Za-z0-9._-]{1,32}`, выбирает host; это ключ дедупликации.
- `operation` — `[a-z.]{1,32}`; ключ — `[a-z_]{1,16}`; значение запроса —
  `[A-Za-z0-9._/:,-]{1,64}`; не больше 8 аргументов; повтор ключа —
  ошибка. Значения ответа могут быть длиннее (список операций).
- `STATE`: `SUCCEEDED`, `FAILED`, `REJECTED` (запрос не принят к
  исполнению: не разобран, неизвестная операция, `ID_REUSED`). Состояния
  `OUTCOME_UNKNOWN` и `CANCELLED` есть в task engine, но гость их сейчас не
  выдаёт (раздел 5).
- Поля, общие для ответов: `code` (при `FAILED`/`REJECTED`), `detail`,
  `effects=none|applied|unknown` (при `FAILED`: были ли изменения),
  `verify=ok|n/a` (проверка конечного состояния; `n/a` — операция без
  эффектов), `checks=<список>` (какие проверки выполнены), `replayed=1`
  (ответ из записи, запрос не исполнялся повторно).
- Ссылка на задачу: `task/<boot_id, 16 hex>/<id задачи>`. `boot_id`
  случаен для каждой загрузки (из TSC); id задач внутри загрузки не
  переиспользуются (m2-kernel.md §5), поэтому пара однозначна и играет
  роль «идентификатор загрузки + поколение» из ARCHITECTURE.md §6.
  Ревизия (`rev`) растёт на каждом событии жизненного цикла задачи.

Коды ошибок: `BAD_REQUEST`, `UNKNOWN_OP`, `ID_REUSED`, `BUSY`,
`STALE_REF` (ссылка из другой загрузки), `NOT_FOUND` (id ещё не выдавался),
`GONE` (задача завершилась), `CONFLICT` (ревизия не совпала с
`expect_rev`), `DENIED` (поток ядра или сам исполнитель), `NO_RESOURCES`,
`KERNEL_ERROR` (ядро отказало до изменения состояния, `detail` — код
`NX_E*`), `TARGET_ENDED`, `VERIFY_FAILED` (вызов прошёл, конечное
состояние не подтвердилось), `RESPONSE_TOO_LARGE`.

## 5. Операции и task engine

| Операция | Аргументы | Вызовы ядра | Проверка конечного состояния | Эффекты / повтор |
| --- | --- | --- | --- | --- |
| `system.describe` | — | `SYS_INFO` | нет (чтение) | нет |
| `task.list` | — | `SOV_TASK_LIST` | исполнитель видит себя `running` | нет |
| `task.inspect` | `target` | `SOV_TASK_LIST` | нет (чтение) | нет |
| `task.spawn` | `program` (файл `bin/<program>` из initramfs) | `SOV_TASK_SPAWN` | задача пользовательская, имя совпадает, жива, **действительно исполнялась** (тики или вызовы > 0, ожидание до 1 с), в журнале ядра есть `created` и `started` для неё | создаёт задачу; повтор с тем же `id` — ответ из записи |
| `task.measure` | `target`, `window_ms` 1–5000 | `TASK_INFO`, `SLEEP`, `TASK_INFO` | задача жива в конце окна, счётчики монотонны, прирост тиков задачи ≤ длины окна | нет |
| `task.terminate` | `target`, необязательно `expect_rev` | `TASK_KILL` | задача не жива, ресурсы освобождены (`reaped`, ожидание до 2 с), `end=killed` и убил именно исполнитель, в журнале есть `killed` и `reaped`, после закрытия handle ядро отвечает на старое значение `EBADHANDLE`, задачи нет среди живых | завершает задачу; повтор — ответ из записи |
| `memory.stats` | — | `SYS_INFO` | нет | нет |
| `event.subscribe` | — | `SYS_INFO` | нет | создаёт курсор (до 4) |
| `event.poll` | `sub` | `SOV_EVENT_READ` | номера событий идут подряд | сдвигает курсор; `lost=` — сколько событий вытеснено из кольца |
| `action.status` | `request` | — | — | служебная, не записывается: `known=yes state=… op=…` или `known=no` |
| `session.close` | `host_checks=ok\|fail`, `reason` | — | — | завершает `bin/core` |

Субъект операции — всегда `bin/core`: ядро определяет его по задаче,
выполняющей системный вызов, и по handle Sovereign, который выдало ему
ядро; ничего в строке запроса полномочий не даёт (ARCHITECTURE.md §5.2).
Таймауты: исполнитель ждёт конечного состояния не дольше указанного выше,
host ждёт ответа 30 с. Отмены нет: операции M3 короткие и исполняются в
одном системном вызове; `CANCELLED`/`COMPENSATING` не реализованы.

**Task engine** (`user/core/engine.c`). На каждый запрос с новым `id` —
запись с жизненным циклом ARCHITECTURE.md §8.2:

```text
CREATED → OBSERVING → PLANNED → RUNNING → VERIFYING → SUCCEEDED
              │           │         │          ├──────→ FAILED
              └───────────┴─────────┴──────────┴──────→ FAILED
                                    └──────────┴──────→ OUTCOME_UNKNOWN
                          PLANNED ─────────────────────→ CANCELLED
```

Недопустимый переход отвергается (`SUCCEEDED` возможен только из
`VERIFYING`; host-тест `test_engine.c`); если исполнитель его всё же
попробует, это считается провалом проверки. Каждый переход печатается в
serial-лог. Запись хранит отпечаток запроса (FNV-1a операции и аргументов)
и полный текст ответа (до 3 КиБ). Повтор того же `id` с тем же отпечатком —
ответ из записи с `replayed=1`, без исполнения; с другим отпечатком —
`REJECTED code=ID_REUSED`. Записей 32; когда все заняты, вытесняется самая
старая завершённая, после чего её `id` снова считается новым — окно
дедупликации ограничено 32 последними запросами.

## 6. Ядро: вызовы 14–21, события, reaper

| № | Вызов | Аргументы → результат | Права |
| ---: | --- | --- | --- |
| 14 | `SLEEP` | `(ticks ≤ 1000)` → 0; 0 — уступить процессор | — |
| 15 | `SYS_INFO` | `(info*)` → 0: `boot_id`, тики, частота, живые задачи, счётчики памяти, `events_next`, `next_task_id` | — |
| 16 | `SOV_TASK_SPAWN` | `(h Sovereign, path*, len, args* или 0)` → handle задачи с правами `INSPECT MANAGE DUPLICATE TRANSFER`; задача сразу запущена | `SOVEREIGN`; путь `bin/[a-z0-9_-]+` |
| 17 | `TASK_INFO` | `(h задачи, info*)` → 0; работает и для завершённой задачи, пока жив handle | `INSPECT` |
| 18 | `SOV_TASK_LIST` | `(h Sovereign, info*, cap ≤ 32)` → число занятых слотов | `SOVEREIGN` |
| 19 | `SOV_EVENT_READ` | `(h Sovereign, since, ev*, cap ≤ 32)` → число событий | `SOVEREIGN` |
| 20 | `CHAN_READ` | `(h канала, buf, cap ≤ 512, timeout ≤ 6000 тиков)` → байты, 0 — таймаут | `READ` |
| 21 | `CHAN_WRITE` | `(h канала, buf, len ≤ 512)` → `len` | `WRITE` |

Новая ошибка: `ENOENT` (12) — нет такой программы в initramfs.

- **События** (`nx_events`, `kernel/obj/event.c`): для пользовательских
  задач — `created`, `started`, `exited` (arg — код), `killed` (arg — id
  убившей задачи, 0 — ядро), `faulted` (arg — вектор), `reaped`. Номера
  1, 2, 3 … без пропусков; кольцо на 128 событий, читатель видит вытеснение
  как `seq` первого события больше запрошенного. Каждое событие увеличивает
  ревизию задачи. События пишутся и в режимах M2, но там не читаются.
- **Reaper** — поток ядра, освобождающий ресурсы задачи, которая
  завершилась, когда её никто не ждёт в `nx_task_wait_reap` (в M2 это делал
  контроллер теста). Запускается только в режимах `m3-*`.
- **Сон**: задача блокируется с моментом пробуждения; обработчик таймера
  будит её. `CHAN_READ` опрашивает UART (до 20000 чтений LSR подряд), затем
  спит 1 тик.
- **`boot_id`**: splitmix64 от TSC при старте режима; под TCG TSC идёт от
  часов host, поэтому две загрузки практически не совпадают. Печатается в
  `NANOX: m3 boot_id=…`.

## 7. Host bridge

- **Адаптеры модели** (`adapters.py`) реализуют `start(request)` и
  `next(observation) → Decision` (инструмент с аргументами или итоговый
  ответ):
  - `mock` — детерминированная сценарная политика, **не языковая модель**:
    узнаёт один запрос («перечисли задачи, запусти нагрузку, измерь,
    останови») и выбирает каждый шаг по предыдущим наблюдениям (ссылку и
    ревизию берёт из ответа гостя); на провал действия останавливается и
    сообщает о нём;
  - `unavailable` — provider, который никогда не отвечает;
  - `anthropic` — Messages API с tool use через `urllib` (только
    стандартная библиотека, как весь стенд): `ANTHROPIC_API_KEY`,
    необязательно `NANOX_MODEL` и `ANTHROPIC_BASE_URL`. Не проверен.
- **Инструменты** модели (`toolspec.py`): `describe_system`, `list_tasks`,
  `inspect_task`, `spawn_task`, `measure_task`, `terminate_task`,
  `memory_stats` — каждый соответствует одной операции NCI. Неизвестный
  инструмент или неполные аргументы host отвергает, не посылая ничего
  гостю, и сообщает модели.
- **Цикл агента** (`agent.py`). Задача host: `CREATED` → (шаги) →
  `SUCCEEDED`, если модель дала итоговый ответ и каждое действие прошло
  проверку; иначе `FAILED` с причиной (`action_failed`,
  `model_unavailable`, `too_many_steps` — больше 12 шагов). Действие с
  эффектами засчитывается только при `SUCCEEDED` и `verify=ok` от гостя.
- **Недоступность модели**: 3 попытки с паузами 0,2 и 0,5 с; каждая
  записывается в трассу; затем задача `FAILED reason=model_unavailable`,
  гостю не отправлено ни одного действия. Гость при этом управляем
  напрямую, без модели (ARCHITECTURE.md §5.4).
- **Потеря ответа** (`call_reliably`): ответ, потерянный в канале, —
  состояние host `OUTCOME_UNKNOWN`. Host не повторяет действие вслепую:
  сначала `action.status`; если гость знает запрос и он завершён, тот же
  запрос посылается ещё раз и получает ответ из записи (`replayed=1`);
  если не знает — запрос не доходил и его можно послать. Потеря
  моделируется на стороне host: ответ читается из сокета и отбрасывается;
  потеря запроса — тем, что он не посылается.
- **Трасса** (`out/runs/<время>-<сценарий>/bridge-trace.jsonl`, схема
  `nanox.bridge-trace.v1`): записи `task` (создание и завершение задачи
  host с итоговым ответом или причиной), `action` (пять частей: `request`,
  `decision` — инструмент, аргументы, обоснование модели; `call` — строка
  NCI; `result` — состояние, поля, строки ответа; `verification` — вердикт
  исполнителя `verify`/`checks` и вердикт host), `recovery` (потерянный
  ответ, `action.status`, как установлен исход), `model` (неудачная попытка
  получить решение), `rejected_tool`. `check_trace` требует все пять частей
  у каждого действия, согласованность вызова с решением и ответа с вызовом и
  завершения каждой задачи. Рядом — `bridge-wire.log` (все строки канала с
  временем) и секция `bridge` в `record.json`. Со стороны гостя трасса
  исполнителя — строки `NANOX: USER core#4: act <id> <операция> <СОСТОЯНИЕ>
  …` в serial-логе (запрос, выбранный вызов, результат, проверка).

Ручной запуск с другим адаптером: `python3 tools/bench/harness.py run
m3-agent --adapter anthropic --echo`.

## 10. Решения M3

1. NCI v1 на уровне Core — строковый формат `key=value`, а не JSON: его
   разбирает пользовательский процесс на C без библиотек; JSON остаётся на
   стороне адаптера модели (ARCHITECTURE.md §7 допускает JSON «для
   диагностики и адаптера модели»).
2. Исполнитель — пользовательский процесс `bin/core` с handle Sovereign, а не
   код ядра: ядро исполняет детерминированные системные вызовы, решения и
   разбор запросов вне его (§5.1).
3. Канал bridge — COM2 с опросом; прерывания UART не используются (нет
   драйвера IOAPIC). Пропускная способность при этом достаточна для
   сценариев (весь сеанс `m3-faults`, 30 запросов, занимает меньше секунды).
4. Ссылка на задачу — `task/<boot_id>/<id>`, поколение — ревизия по
   событиям; устаревшая ссылка определяется по `boot_id` (другая загрузка) и
   по тому, что id меньше `next_task_id`, но задачи нет среди живых.
5. Дедупликация — в исполнителе, по `id` запроса и отпечатку, окно 32
   запроса. Ответ хранится целиком, повтор отвечает тем же текстом.
6. Проверка конечного состояния берёт данные из двух источников ядра:
   состояние задачи (`TASK_INFO`, `SOV_TASK_LIST`) и журнал событий.
7. Операции без эффектов отмечаются `verify=n/a`; действие с эффектами
   засчитывается host только при `verify=ok`.
8. Итог host-проверок передаётся гостю в `session.close` и превращается в
   код выхода `bin/core`, чтобы вердикт прогона оставался в конвенции
   маркер + код выхода (m0-bench.md §6).
9. Потеря ответа моделируется на стороне host, потеря запроса — отказом от
   отправки; повреждение байтов в канале не моделируется.
10. Отказ модели — 3 попытки с короткими паузами; политика повторов
    provider (коды HTTP, `retry-after`) не реализована.

## 11. Что проверено при подготовке этого шага

Эталонная среда та же (Ubuntu 24.04, clang/lld 18.1.3, QEMU 8.2.2, TCG, без
KVM). В рабочем дереве выполнено:

- `make doctor && make && make test` — код выхода 0: host-тесты C (794
  проверки, UBSan в режиме trap), 55 Python-тестов, 33 сценария QEMU (8 M0,
  13 M1, 5 M2, 7 M3) с ожидаемыми вердиктами, повторяемость `normal`,
  `pagefault`, `m2-sched`;
- host-тесты дополнительно собраны gcc с `-fsanitize=address,undefined`;
- `make repro-check` — `BOOTX64.EFI`, `kernel.elf`, `initrd.img` (с
  `bin/core` и `bin/load`) и `nanox.img` побайтово совпали в трёх сборках;
- `make debug-check` — GDB остановился в `kernel_main`.
- после публикации ветки: `make doctor && make && make test` в свежем
  `git clone` — код выхода 0, те же 794 проверки, 55 Python-тестов и 33
  сценария;
- промежуточный коммит только гостевой части (без host bridge) отдельно
  проходит `make test` (26 сценариев M0–M2).

Что входит в `make test` для M3:

- host-тесты C: журнал событий (порядок, вытеснение из кольца, выключенный
  журнал), разбор и сборка строк NCI (все ошибки разбора, границы длины,
  отпечатки, ссылки), task engine (все допустимые и запрещённые переходы,
  повтор, `ID_REUSED`, вытеснение, режим без дедупликации);
- Python-тесты `test_bridge.py`: формат строк, клиент поверх пары сокетов с
  имитацией гостя (шум прошивки до `HELLO`, таймаут), восстановление после
  потери ответа с дедупликацией и без неё, таблица инструментов, мок-модель,
  отказ модели без отправки действий, вердикты действий, полнота трассы,
  ожидания harness `expect.bridge`;
- 7 сценариев QEMU этого раздела.

Чувствительность host-тестов: в проверяемый ими код M3 по одной вносились 8
ошибок (переход `RUNNING → SUCCEEDED`, пропуск сверки отпечатка,
вытеснение самой новой записи вместо старой, запись событий при
выключенном журнале, повтор ключа, ссылка с id 0, сдвиг границы кольца,
удаление разделителя в отпечатке). Шесть обнаружены; две последние
оказались эквивалентными (поведение не меняется), что проверено разбором
кода.

## 12. Что не проверено

- **Настоящая модель.** Адаптер `anthropic` написан по документации API
  (Messages API, tool use, адаптивное мышление), но ни разу не выполнялся
  против provider: в среде подготовки нет ключа. Поэтому критерий 3 («ИИ по
  запросу …») не отмечен, а готовность M3 не достигнута. Цепочка
  «запрос → решение → действие в ядре → проверка → трасса» проверена только
  с мок-моделью, которая не является ИИ.
- Состояния `OUTCOME_UNKNOWN` и `CANCELLED` у гостя не возникают; отмена
  операций и компенсация не реализованы.
- Переполнение журнала событий (больше 128 событий между опросами) в QEMU не
  проверялось, только host-тестами; вытеснение записей task engine (больше
  32 запросов между повторами) — тоже только host-тестами.
- Устойчивость разбора строк к произвольным и враждебным данным канала не
  проверялась (в объём не входят атакующие тесты); проверены только
  перечисленные в `m3-nci` и `test_nci.c` некорректные запросы.
- Обрыв канала посреди сеанса, повреждённые байты, медленный host: не
  моделировались. Исполнитель завершается сам, если 120 с нет запросов;
  этот путь не выполнялся.
- `task.measure` и `task.terminate` для задач, не запущенных исполнителем
  (через `SOV_TASK_OPEN`), и `DENIED` для потоков ядра в сценариях не
  выполнялись.
- Повторяемость (`harness.py repeat`) для сценариев M3 не настраивалась:
  `boot_id`, тики и доля CPU меняются от запуска к запуску.
- Критерии M2 4–6 этим этапом не закрываются: сценарии M3 выполняют
  `TASK_KILL` через handle, полученный `SOV_TASK_SPAWN`, но
  привилегированная операция Sovereign над чужой задачей, изоляция и
  некорректные системные вызовы отдельно не проверялись.
- Все результаты получены в QEMU (TCG) и не доказывают работу на реальном
  оборудовании.
