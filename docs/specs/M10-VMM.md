# M10: VMM для испытания кандидатов (AMD-V)

Статус: рабочий контракт, 2026-09-28. Владелец — Claude (M0–M8 ведёт Codex).
Ни один критерий M10 в [ROADMAP](../ROADMAP.md) этим не закрывается: код
проверен на скриптовой модели процессора и зондом `svm-probe` на SVM в
QEMU TCG (§4a), ядро M0 загружается гостем и даёт тот же вердикт и serial,
что в QEMU (§4b); ядро NANOX VMRUN не выполняет, на Ryzen не запускалось.

## 1. Зачем

Критерий 4 M10: «портирован эмулятор или реализован ограниченный VMM для
тестирования кандидатов». Сейчас кандидат испытывается в QEMU на host
(`cargo xtask test`). Внутри NANOX QEMU нет, поэтому нужен собственный VMM,
который запускает кандидат как гостя и выдаёт тот же вердикт, что harness
M0: запись значения `v` в порт `isa-debug-exit` (0xF4) даёт статус
`(v << 1) | 1` (33 — PASS, 35 — FAIL), serial COM1 захватывается.

Целевой ноутбук — AMD Ryzen 7 5800H, поэтому AMD-V (SVM), не VMX.

## 2. Что сделано: `crates/hw-svm`

`no_std`, без `alloc` и сторонних crates, `forbid(unsafe_code)`.
Привилегированные инструкции (VMRUN, VMLOAD/VMSAVE, CPUID, RDMSR) выполняет
ядро через трейт `SvmCpu`; crate их не исполняет.

| Модуль | Содержание |
|---|---|
| `caps` | CPUID Fn8000_0001/Fn8000_000A и VM_CR: SVM есть, не выключен firmware (с учётом LOCK), есть nested paging и ≥ 2 ASID |
| `vmcb` | VMCB 4 KiB с типизированными полями, настройка 64-битного гостя, проверки консистентности VMRUN (APM 15.5.1) плюс требования VMM (nested paging, nCR3) — каждое нарушение отдельной ошибкой до VMRUN |
| `perm` | карты разрешений MSR (8 KiB, три диапазона) и портов (12 KiB, с битами для доступов за FFFFh) |
| `npt` | вложенные таблицы 4 уровня: map без частичного эффекта (подсчёт недостающих таблиц, предвыделение цепочкой в самих кадрах), unmap с токеном «нужен сброс TLB», translate, destroy |
| `exit` | декодирование #VMEXIT: INTR/NMI/SMI/INIT, CPUID, HLT, IOIO (порт, размер, STR/REP, next RIP), MSR, SHUTDOWN, VMMCALL, SVM-инструкции, NPF, исключения, INVALID |
| `vmm` | цикл vCPU: перехват всех портов и MSR вне списка (PAT, STAR/LSTAR/CSTAR/SFMASK, FS/GS/KernelGS base, TSC_AUX), CPUID с битом гипервизора, без SVM/VMX/x2APIC/MONITOR/TSC-deadline и с листом 4000_0000h «NanoxVMM», #GP для прочих MSR, #UD для VMMCALL и SVM-инструкций, передача COM1, debug-exit, бюджеты по выходам и времени, сброс TLB через TLB_CONTROL после unmap |

Вердикты: `DebugExit {value, status}`, `Shutdown` (тройная ошибка),
`Halted`, `Timeout`, `ExitBudget`, `NestedPageFault {gpa, error}`,
`UnsupportedIo`, `UnhandledExit`, `Invalid(StateError)`.

## 3. Проверка

`crates/hw-svm/tests/svm.rs`, 23 теста на скриптовом процессоре
(`tests/common/mod.rs`). Он отказывает в VMRUN при неверном состоянии,
учитывает TLB_CONTROL и кэширует трансляции, сам (независимо от crate)
проходит вложенные таблицы, читает карты разрешений по адресам из VMCB и
проверяет, что VMM правильно сдвинул RIP или внёс исключение. Проверено:
все 17 проверок консистентности, раскладка карт разрешений, границы и
откат NPT, обнаружение порчи записей, прохождение кандидата со статусом 33
и FAIL со статусом 35, чтения портов (IN EAX обнуляет старшую половину RAX
— дефект, найденный при написании тестов), политика CPUID и MSR, #UD,
NPF на отсутствующей и read-only странице, бюджеты, переполнение serial,
работа без NRIP. Негативный контроль: без сброса TLB после unmap гость
продолжает читать старую страницу. Мутационная проверка: шесть мутантов
(нет сброса TLB, нет обнуления RAX, нет бита гипервизора, таблицы без U/S,
нет проверки ASID, потеря кадров при нехватке) проваливают набор.

## 4. Чего не хватает до настоящего испытания кандидата

1. **Загрузка кандидата в гостя** — сделано для handoff M0 (BootInfo v1):
   `crates/guest-boot` (§4b). При изменении BootInfo или handoff (зона
   Codex) `guest-boot` должен меняться вместе с `boot/uefi`; его тесты
   проверяют результат валидаторами `boot-protocol`, так что расхождение
   будет видно. Initramfs (KIND_INITRAMFS) пока не передаётся.
2. **Виртуальный таймер и прерывания.** Ядро M1 использует LAPIC timer;
   без эмуляции LAPIC (или AVIC) гость с таймером работать не будет.
3. **Ядерная часть.** Трейт `SvmCpu` в ядре: включение EFER.SVME,
   VM_HSAVE_PA, VMLOAD/VMRUN/VMSAVE на ассемблере с сохранением GPR,
   выделение VMCB, карт и кадров через PMM M1.
4. **Проверка на железе.** VMRUN на Ryzen 7 5800H — только после загрузки
   NANOX на ноутбуке (M9) и отдельного задания владельца.
5. **Сравнение с QEMU** — выполнено для ядра M0 в четырёх сценариях
   (§4b): одинаковый статус и serial. Для ядер M1+ (таймер, прерывания)
   сначала нужен пункт 2.

## 4a. Исполнение на SVM: `tools/svm-probe` (2026-09-28)

`svm-probe` — UEFI-приложение (`x86_64-unknown-uefi`), которое запускает
hw-svm на настоящей реализации SVM вместо скриптового процессора. Ядро
Codex не используется: зонд работает под OVMF на CPL 0 с тождественным
отображением памяти, сам выполняет CLGI/VMSAVE/VMLOAD/VMRUN/VMSAVE/VMLOAD/
STGI (`src/hw.rs`), берёт страницы из собственного статического пула и
завершает QEMU через isa-debug-exit (33 — все случаи совпали, 35 — нет).
Гостевые программы собраны ассемблером (`src/guest.rs`) и копируются в
память гостя; вложенные таблицы отображают только кадры пула.

Запуск (внутри `nix develop`): `python3 tools/svm-probe/run.py`. Профили:

| Профиль | `-cpu` | Ожидание |
|---|---|---|
| svm | `qemu64,+svm,+npt,+nrip-save,+flushbyasid,+vmcb-clean` | статус 33, `RESULT PASS` |
| milan | `EPYC-Milan` с теми же флагами (Zen 3, как Ryzen 7 5800H) | статус 33, `RESULT PASS` |
| no-svm | `qemu64,-svm` | статус 35, `UNAVAILABLE NotSupported` |

Результат `out/svm-probe-20260928T170909Z/`: все три профиля совпали.
Гостевые случаи на настоящем VMRUN с вложенными таблицами:

- `basic` — COM1, чтение LSR через `IN EAX`, CPUID с листом «NanoxVMM» и
  битом гипервизора, без SVM у гостя, запись через гостевые и вложенные
  таблицы (хост проверяет байты в кадре), RDMSR/WRMSR PAT без выхода →
  статус 33;
- `fail` → 35; `npf-absent` (0x100000, не присутствует, финальная
  трансляция) и `npf-readonly` (запись в RO-страницу) → NPF с верными
  кодами; `ud2` без IDT → тройная ошибка → Shutdown; `hlt` → Halted;
  `msr-denied` → #GP → Shutdown; `vmmcall` → #UD → Shutdown;
- `remap` — останов, замена кадра за GPA 0x9000, продолжение: гость видит
  новый байт («AB»).

Базовое состояние, которое строят `setup_long_mode` и `prepare`,
процессор принимает. Из 15 нарушений, поданных процессору (два
собственных требования VMM не подаются: гость получил бы доступ к памяти
хоста), 13 отвергаются и `Vmcb::check`, и процессором. Два расхождения
ожидаемы: невыровненный IOPM (hw-svm строже; процессор игнорирует
младшие биты) и исключение с вектором 31 (QEMU отвергает `vector >= 31`,
по APM допустимы 0–31; hw-svm следует APM, verify).

Негативные проверки: профиль без SVM сообщает о недоступности и не
проходит; мутант hw-svm без перехвата портов позволяет гостю писать
прямо в serial и в isa-debug-exit — QEMU завершается без
`RESULT PASS`, раннер возвращает 1.

Найдено и исправлено исполнением:

1. **VMEXIT_INVALID приходит как `0xFFFF_FFFF`**: QEMU записывает
   32-битный −1 (Linux KVM тоже сравнивает только младшую половину
   EXITCODE). `Exit::decode` распознаёт обе формы (`code::INVALID_32`).
2. **FlushByAsid не всегда есть** (в QEMU TCG нет, как и NRIP save и
   VMCB clean). `VmConfig::flush_by_asid` из `SvmCaps`; без него unmap
   сбрасывает весь TLB (TLB_CONTROL 1), а не значение 3.
3. **EVENTINJ**: NMI с любым вектором допустим, исключение с вектором 2
   или > 31 — нет (раньше было наоборот; сверено с QEMU `svm_helper.c`).
4. `Vmcb::as_mut_ptr` — указатель на страницу VMCB для ядерного пути
   VMRUN (процессор пишет VMCB через него).

Не проверено исполнением: VMCB clean bits, NRIP save, decode assists (TCG
их не даёт), сброс TLB по ASID (QEMU сбрасывает весь TLB при загрузке CR3
гостя, поэтому `remap` проходит и без токена — отрицательный контроль
сброса остаётся только в host-тестах), перехват INTR (зонд работает с
выключенными прерываниями). Адреса карт и CR3 hw-svm ограничивает 2^52,
процессор — `phys_bits` из CPUID 8000_0008 (hw-svm строже только сверху
через 2^52; ниже `phys_bits` пока не проверяет).

## 4b. Кандидат M0 как гость: `crates/guest-boot` (2026-09-29)

`guest-boot` (`no_std`, без `alloc`, `forbid(unsafe_code)`, зависит только
от `boot-protocol`) строит в памяти гостя то же, что `boot/uefi` перед
передачей управления ядру: сегменты ELF (разбор — `boot_protocol::elf`),
арену 256 KiB с BootInfo, резервами, сегментами и картой памяти по тем же
смещениям, стек 64 KiB со страницей-ловушкой, таблицы страниц (W^X, NX на
данных, без тождественного отображения) и страницу transition, которую
требует `validate_buffers`. Вход: RIP = entry, RSP = `STACK_TOP`, RDI =
`HANDOFF_BASE`, CR3 = PML4 гостя. Раскладка считается и проверяется до
первой записи: ошибка не оставляет следов в памяти гостя.

Тесты (5): результат проверяется собственными валидаторами
`boot-protocol` (`validate_header_at`, `validate_buffers` — то же, что
ядро M0 делает при входе), причём буферы читаются через независимый обход
построенных таблиц; сегменты, нули BSS, W^X/NX, страница-ловушка, карта
памяти без дыр, отказ без записи, минимальный размер RAM, совпадение
кодирования BootInfo с `repr(C)`. Мутационная проверка: пять мутантов (нет
NX, стек не зарезервирован, неверный `pml4_phys`, нет обнуления, ошибка
проверки размера на страницу) проваливают набор.

**Настоящее ядро M0 под VMM.** Раннер передаёт `out/KERNEL.ELF` зонду
через fw_cfg; зонд даёт гостю 4 MiB RAM, строит handoff и запускает ядро
(`m0-*` в `out/svm-probe-20260928T233339Z/`):

| Случай | Эпоха | Вердикт VMM | Serial ядра |
|---|---|---|---|
| m0-pass | 20260922 | статус 33 | `BOOTINFO_VALIDATED`, `NANOX:TEST:PASS` |
| m0-fail | u64::MAX | статус 35 | `NANOX:TEST:FAIL:injected` |
| m0-panic | u64::MAX−2 | статус 35 | `NANOX:KERNEL:PANIC:…` |
| m0-hang | u64::MAX−1 | Halted | `NANOX:TEST:HANG:injected` |
| m0-normal-profile | без test profile | Halted | `NANOX:KERNEL:IDLE`, без `NANOX:TEST` |
| m0-bad-handoff | резерв transition испорчен | статус 35 | `BOOTINFO_ERROR:Ownership` |

Сравнение с QEMU: для pass/fail/panic/hang serial ядра под VMM построчно
равен serial последней записи M0 (`out/runs/*-<scenario>-boot-test`) с тем
же `KERNEL.ELF` (хэш сверяется); в строке `map_bytes=…` сравниваются
`descriptor_stride`, `segments` и `epoch`, остальное зависит от раскладки
(в QEMU карта памяти OVMF — 5424 байта и 9 резервов, у VMM — 144 байта и
7 резервов). Статусы совпадают (33/35/35; зависание — timeout в QEMU,
Halted у VMM).

Найдено сравнением: ядро пишет делитель (1) в порт 0x3F8 при LCR.DLAB = 1,
и VMM записывал его в serial лишним байтом `\x01`. Эмуляция 16550 теперь
учитывает DLAB (тест `divisor_latch_writes_are_not_serial_output`); до
исправления сравнение давало `equal=False` — естественный отрицательный
контроль.

## 5. Порядок

VMRUN проверен зондом (§4a), кандидат M0 загружается гостем и совпадает с
QEMU (§4b) — всё без ядра NANOX. Дальше: пункт 2 (виртуальный LAPIC timer)
для ядер M1+, пункт 3 в ядре по образцу `svm-probe/src/hw.rs` (зона ядра
— Codex, нужна договорённость). `svm-probe` можно загрузить на ноутбуке с
USB для проверки на Zen 3 — только по отдельному заданию владельца.
