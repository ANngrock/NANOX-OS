# M11: режим сервера, переключатель и Proxmox

Статус: рабочий контракт, 2026-09-30. Владелец — Claude (M0–M8 ведёт Codex).
Ни один критерий M11 в [ROADMAP](../ROADMAP.md) этим не закрыт: есть host-срезы
(`qga`, `svc`, `vswitch`, §6) и проверка загрузки образа M0 в конфигурации, как
у Proxmox. Ядра с virtio, сетью и процессами (M2–M5) для настоящих критериев
пока нет.

## 1. Цель и толкование задания

Владелец: ОС должна работать как обычная ОС и параллельно как круглосуточный
сервер, почти не теряя ресурсов, размещать разные службы и интегрироваться с
Proxmox; нужен «свитч». Толкование (проверить у владельца):

- **Переключатель режима** — командой и (после M7) элементом интерфейса
  выбирается режим; сервер и рабочий стол делят машину без перезагрузки.
- **Виртуальный L2-коммутатор** — сеть между службами и внешней сетью (в
  Proxmox для этого служат Linux bridge `vmbr*`). Делается как часть сети
  служб, если «свитч» означал его.

## 2. Режимы

| Режим | Интерактивная часть | Службы | Назначение |
|---|---|---|---|
| desktop | полный приоритет | только помеченные `always` и с малым бюджетом | обычная работа |
| hybrid | приоритет, но с гарантированным резервом службам | по манифесту, в пределах резерва | ноутбук как рабочая станция и сервер |
| server | не запускается (нет компоновщика окон, нет ввода) | все, полный бюджет | headless, экономия памяти и CPU |

Инварианты (проверяемые тестами `crates/svc`):

1. Переключение — атомарный переход: либо режим сменился целиком, либо
   остался прежним и причина возвращена (нет полу-состояния).
2. Службы с `always` не останавливаются при любом переходе; остальные
   останавливаются с драйнингом (SIGTERM-эквивалент, затем таймаут).
3. Сумма резервов служб не превышает доли хоста, разрешённой режимом; резерв
   не отбирается у службы, пока она в пределах бюджета (гарантия), и не
   нарушает потолок интерактивной части в hybrid.
4. Переход server → desktop/hybrid запускает интерактивную часть последней;
   обратный — останавливает её первой.
5. Перезагрузка возвращает режим из сохранённой конфигурации; неверная
   конфигурация даёт безопасный режим server без сетевых служб (ошибка в
   журнал), а не отказ загрузки.

## 3. Службы и ресурсы

Манифест: имя, хэш образа, capabilities, зависимости, `restart` (never |
on-failure | always) с backoff (начало, множитель, предел, окно
crash-loop), health-check (интервал, таймаут, порог), лимиты: CPU shares и
квота, память (жёсткий предел и резерв), ввод-вывод, порты (только объявленные).
Supervisor — детерминированный автомат на виртуальном времени (`Clock`), как
устройства VMM: то же прошлое даёт то же поведение, тесты воспроизводимы.

Ресурсная модель («не терять ресурсов»): простой служб стоит один tickless-
таймер на ближайший дедлайн; измеряется накладными расходами простоя (число
пробуждений в секунду и байт памяти supervisor'а) — это критерий 3 этапа, не
обещание. Пока измерить можно только модель, не ядро.

## 4. Интеграция с Proxmox VE

Уровень 1 (обязательный): NANOX — гость Proxmox. Proxmox управляет гостем тем,
что даёт QEMU/KVM; гостю нужно:

| Что Proxmox использует | Что нужно от NANOX | Статус |
|---|---|---|
| Машина q35 + OVMF (`bios: ovmf`, `machine: q35`) | уже профиль M0 | проверено (M0), §6 |
| Диск `virtio-scsi-single` | загрузка с него (loader читает ESP через UEFI) | проверено загрузкой образа M0, §6 |
| `qm shutdown` (ACPI power button) | обработчик SCI/PM1, S5 через PM1a_CNT из FADT | нет: отрицательный результат записан (§6); нужны M1+, hw-acpi разбирает FADT |
| QEMU Guest Agent (`agent: 1`) | канал virtio-serial `org.qemu.guest_agent.0` и протокол | протокол: `crates/qga` (сверен с `qemu-ga`); канал в ядре нет |
| Сеть `virtio-net` + bridge | драйвер и стек (M5) | нет |
| Watchdog `i6300esb` | драйвер и питание таймера службой | нет |
| Балун `virtio-balloon` | необязателен | нет |
| Cloud-init/конфигурация | необязательно, отдельное решение | нет |

`tools/proxmox/` строит командную строку QEMU по образцу `qm showcmd` и
проверяет, что образ M0 в ней загружается с тем же вердиктом.

Уровень 2 (позже, по решению): клиент REST API Proxmox для самоуправления
(snapshot перед обновлением). Отложен: требует TLS и аутентификации на
стороне гостя (M5).

Безопасность гостевого агента: канал доверенный со стороны хоста, но команды
ограничены allowlist'ом; `guest-exec`, `guest-file-*`, `guest-set-user-password`
по умолчанию отключены (как в `qemu-ga --block-rpcs`).

## 5. Виртуальный коммутатор

`crates/vswitch`: обучающийся L2-коммутатор (MAC-таблица с возрастом и лимитом,
флуд неизвестных и широковещательных, VLAN access/trunk, порт-изоляция),
детерминированный на виртуальном времени; защита таблицы от переполнения и
петель (кадр с собственным MAC порта отбрасывается, STP не моделируется и не
заявляется).

## 6. Проверка (host-срез, 2026-09-30)

**`crates/qga`** (13 тестов, 7 мутантов пойманы): протокол гостевого агента.
Ответы 39 запросов побайтно совпадают с настоящим `qemu-ga` 9.2.4 —
`tools/proxmox/capture_qga.py` запускает его на unix-сокете (опасные команды
заблокированы `-b`) и снимает пары запрос/ответ в
`crates/qga/tests/fixtures/qemu-ga-9.2.4.json`. Совпадают: порядок ключей
(в ошибках `id` первым, в успехе последним), разделители `", "`/`": "`,
экранирование не-ASCII как `\uXXXX` заглавными, тексты всех замеченных
ошибок разбора и проверки аргументов, «disabled» для блокированных команд,
эхо `id` любого типа. Пять структурных ответов (`guest-info`, время, имя
хоста, ОС, интерфейсы) сравниваются по форме. Идентифицирующие значения
хоста (имя, адреса, MAC) в фикстуры не пишутся; скрипт отказывается
сохранять «точный» ответ, похожий на адрес. IPv6 в каноническом виде
проверен против `std` на 20 000 случайных адресов; 60 000 мутированных
сообщений не вызывают паник, и каждый ответ — корректный JSON. Реализовано
12 команд, среди них всё, что нужно Proxmox при `agent: 1` (ping, info,
network, osinfo, time, shutdown, fsfreeze). Не реализовано (отвечают
«disabled»): exec, файлы, пароль, ssh, vcpus, память, suspend, trim,
`get-fsinfo` (Proxmox без него не показывает занятость дисков).
Не проверено против эталона (помечено `(unverified)` в коде): текст
ошибки неверного `mode` у shutdown, список команд, разрешённых при
заморозке, повторное `freeze`.

**`crates/svc`** (26 тестов, 9 из 10 мутантов пойманы; десятый эквивалентен):
режимы, переключение, supervisor. Сценарии: порядок запуска по
зависимостям и готовности, ready-timeout, backoff 100→800 мс и его сброс
после стабильной работы, crash-loop → `Failed` с ручным восстановлением,
политики перезапуска, отказ запуска как сбой, health-check с таймаутом и
серией отказов, эскалация остановки до kill, каскад при падении
зависимости и перезапуск зависимых, ручной stop/start/restart зависимостей,
остановка оболочки первой и запуск последней (в том числе когда служба
ждёт готовности зависимости, но не когда она заблокирована упавшей),
отказ переключения сверх бюджета без единого вызова платформы, запрет
запусков, которые превысили бы резервы, пока служб старого режима ещё
останавливаются, безопасная загрузка при повреждённой записи режима
(каждый одиночный бит записи ловится CRC-32), tickless-простой (нет
запланированного — нет пробуждений; 12 служб с health-check раз в 10 с —
~360 пробуждений в час на всех вместе; сам supervisor меньше 8 KiB) и
40 случайных последовательностей по 1 500 операций с проверкой инвариантов
после каждого шага и полной сходимостью в конце. Распределитель CPU
(`share`): 200 000 случайных наборов; проверены гарантия резерва, потолок,
работа без простоя, пропорциональность по весам. Гарантия задержки
интерактивной части в hybrid сведена к этому свойству: её резерв нельзя
отобрать, что бы ни просили службы.

**`crates/vswitch`** (12 тестов, 10 из 10 мутантов пойманы): обучение и
старение MAC, флуд неизвестных и широковещательных, VLAN access/trunk с
перезаписью тегов (`emit`), изоляция портов, лимит MAC на порт, демпфирование
«прыжков» MAC, отсев рантов, слишком больших кадров, multicast-источника и
зарезервированной группы 01-80-C2-00-00-0x, ограниченная таблица при
потоке из 30 000 адресов, сверка с эталонной моделью на 200 000 кадров и
инварианты (кадр не уходит обратно, VLAN не протекает, тег ровно там, где
нужно) на 300 случайных конфигурациях. STP нет и не заявляется.

**`tools/proxmox`**: `pve_qemu.py` строит командную строку по образцу
`qm showcmd` (q35, OVMF в двух pflash, `virtio-scsi-pci` + `scsi-hd` с
bootindex, канал `org.qemu.guest_agent.0` на virtio-serial, virtio-net,
balloon, rng, `i6300esb` с `-watchdog-action reset`, VGA), 9 unit-тестов
формы; `boot_check.py` загружает в ней образ M0 из прогона `xtask test`.
Результат (`out/proxmox-20260930T122410Z`, QEMU 9.2.4 под TCG):

| Случай | Итог |
|---|---|
| min (только virtio-scsi), 1 vCPU | статус 33, `NANOX:TEST:PASS`, 2 с |
| min, 2 vCPU | статус 33, PASS |
| full (все устройства выше), 1 vCPU | статус 33, PASS, канал QGA принимает подключение |
| full, 2 vCPU | статус 33, PASS |
| ACPI shutdown (`system_powerdown`) на образе без тестового BOOT.CFG | **не обработано**: ядро дошло до `KERNEL:IDLE`, после команды ВМ осталась `running` |

Замечания: (1) `-no-shutdown` Proxmox всегда передаёт; с ним закреплённый
QEMU не завершается по isa-debug-exit, поэтому загрузочный вердикт снимается
без него (флаг `no_shutdown` только в ACPI-случае); (2) в закреплённом QEMU
нет ни slirp, ни TAP, сеть — `hubport`; (3) отрицательный результат ACPI —
критерий для будущего драйвера: `boot_check.py --expect-acpi-shutdown`
должен тогда проходить.

Не сделано: любой запуск на Proxmox VE (KVM, TAP, реальный `qm`), драйверы
virtio-serial/net/balloon/watchdog и обработчик ACPI в ядре, soak-прогон,
служба, доступная из сети, интеграция supervisor'а и vswitch в ядро.

## 7. Порядок

После M1–M5 Codex: virtio-serial и QGA-канал в ядре → ACPI shutdown → сеть и
vswitch на настоящем virtio-net → supervisor в userspace (M2) → soak в QEMU и
затем на Proxmox VE (нужен стенд владельца).
