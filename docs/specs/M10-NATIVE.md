# M10: native userspace target и runtime-слой

Статус: определение, измерение и часть реализации, 2026-09-30. Закрывает
первый критерий M10 как **определение**, проверенное сборкой и проверкой ELF;
остальные критерии M10 не закрыты (раздел 8). Ядра с userspace ещё нет (M2,
Codex): всё, что требует syscall, здесь только описано.

## 1. Три уровня

| уровень | что | состояние |
|---|---|---|
| **T0, сейчас** | `x86_64-unknown-none` стабильного rustc 1.90 + флаги пользователя (`tools/native/build.py`), только `core` и `alloc`, библиотека `crates/runtime` | собирается, ELF проверен |
| **T1, custom target** | `x86_64-unknown-nanox` ([user/x86_64-unknown-nanox.json](../../user/x86_64-unknown-nanox.json)): `os = "nanox"`, малая модель кода, статическая перемещаемость; нужен для `std` и для сборки собственной `core`/`alloc` | спецификация принята rustc (`--print cfg`), собрать под неё нечем: нужен `-Zbuild-std` |
| **T2, std/libc** | слой, без которого rustc, cargo и линкер внутри NANOX не запустятся | определён и измерен (раздел 6), не реализован |

T0 использует собранные заранее библиотеки целевой платформы с моделью кода
`kernel`: её 32-битные абсолютные адреса со знаком покрывают и нижние 2 ГиБ, где
живут пользовательские программы (0x400000), поэтому программа по T0 корректна.
Малая модель кода (`code-model = small`) несовместима с этими библиотеками при
LTO (проверено: ошибка слияния флагов модуля) и приходит вместе с T1.

## 2. Что определяется для программы

- **Аппаратный профиль:** x86-64, программный вещественный ABI (как у ядра): SSE и
  x87 выключены, пока ядро не сохраняет их состояние; `panic = abort`;
  перехвата исключений и unwinding нет.
- **Адреса:** код начинается с 0x400000; пользовательский диапазон
  `0x400000 .. 0x7FFF_FFFF_0000`; ядро и верхняя половина недоступны.
- **Стек:** создаёт загрузчик, указатель 16-байтно выровнен до перехода,
  исполнять код на нём нельзя (PT_GNU_STACK без X).
- **Куча:** программа получает память у ядра через `memory_map` (ABI-NCI §4) и
  отдаёт её `LockedHeap`; до первой нехватки куча может быть нулевой. Крейт ждёт
  от слоя syscall одну функцию (`GrowHook`), ничего больше.
- **Завершение:** `thread_exit` (ABI-NCI §4); до появления слоя syscall эту
  точку заполняет программа (`nanox_exit`).
- **Без libc:** native-программы не используют C-библиотеку. Функции `memcpy`,
  `memmove`, `memset`, `memcmp`, `bcmp`, которые компилятор вставляет сам,
  даёт `crates/runtime` (`rep movsb`/`rep stosb`, сравнение через volatile: так
  компилятор не превратит их обратно в вызов самих себя).

## 3. Контракт ELF

Проверяется `tools/native/check_elf.py` (9 тестов, включая 20 000 испорченных
файлов без исключений) и применяется загрузчиком M2:

1. ELF64, little-endian, `ET_EXEC`, `EM_X86_64`, версия 1, файл ≤ 16 МиБ.
2. Таблица заголовков: запись 56 байт, 1–16 записей, целиком внутри файла.
3. Каждый `PT_LOAD`: внутри пользовательского диапазона; адрес и смещение в файле
   совпадают по модулю 4096; выравнивание кратно 4096; часть в файле не больше
   части в памяти и внутри файла; читаем; **не одновременно W и X**; суммарно
   ≤ 256 МиБ; соседние сегменты не делят страницу.
4. Точка входа лежит в исполняемом сегменте, в той его части, что есть в файле.
5. Есть `PT_GNU_STACK`, он не исполняемый.
6. Нет `PT_INTERP`, `PT_DYNAMIC`, `PT_SHLIB`, `PT_TLS` (хранилище потока пока не
   поддерживается).
7. Нет секций перемещений (`SHT_REL`/`SHT_RELA`) и динамической секции: программа
   полностью скомпонована.

Скрипт компоновки [user/link.ld](../../user/link.ld): три `PT_LOAD` (R+X, R, R+W),
`.text.entry` первым, `.bss` без файла. Образец `user/hello` собран и
соответствует: точка входа 0x400000, три сегмента, стек RW.

## 4. Запуск процесса: startup blob

Загрузчик передаёт в RDI указатель, в RSI длину блока только для чтения
(**предложение**: его нужно согласовать с загрузчиком M2). Малый endian, заголовок
32 байта, поля `magic "NXSI"`, `version 1`, `header_len`, `total_len`, `flags = 0`,
область аргументов (NUL-терминированные строки) и таблица **именованных**
handles (16 байт имени, printable ASCII + 8 байт handle ≠ 0). Имена, а не номера
слотов, говорят, что это за handle, поэтому загрузчику и программе не нужно
согласовывать порядок. Полный формат — в документации модуля `start`. Разбор
проверяет границы, переполнение, пересечение областей, терминаторы, имена,
повторы и нулевые handles; неверный блок отвергается целиком. Входная точка
`_start` (feature `entry`, x86-64): обнуляет RBP, выравнивает стек, вызывает
`rust_entry(info, len)`, которая передаёт `StartInfo` в `nanox_main` (макрос
`nanox_entry!`) и завершает процесс кодом возврата (127, если блок неверен).

## 5. Библиотека `crates/runtime`

| модуль | что | unsafe |
|---|---|---|
| `heap` | куча первого подходящего по упорядоченному списку свободных блоков; слияние с обоими соседями; отказ при повторном освобождении; `LockedHeap` как `GlobalAlloc` со спин-замком и крючком роста (`GrowHook`) | да: список в самой свободной памяти |
| `mem` | `memcpy`/`memmove`/`memset`/`memcmp`/`bcmp` (C-символы по feature `mem-symbols`, никогда в тестах хоста) | да: встроенный ассемблер |
| `start` | startup blob, разбор и кодирование, `_start` и `nanox_entry!` (feature `entry`) | только вход |

Без зависимостей, `no_std`, без аллокаций в разборе блока. Проверка: 22 теста
(куча — против теневой модели на 240 000 случайных операций с проверкой
инвариантов списка после операций, выравнивания до 4096, содержимого блоков,
полного слияния, повторного освобождения, роста через крючок и четырёх потоков;
память — против стандартной библиотеки на всех размерах, выравниваниях и
перекрытиях; блок запуска — все усечения, 200 000 повреждённых блоков), мутации
(раздел 7), `clippy -D warnings`, сборка под `x86_64-unknown-none`.

## 6. Внешняя поверхность: что нужно, чтобы запустить инструменты

Измерено `tools/native/surface.py` на этом тулчейне (Nix, glibc, rustc 1.90.0);
данные — [docs/research/native-surface/](../research/native-surface/). Это
измерение, а не нижняя граница.

**Функции libc, которые импортируют бинарники инструментов** (cargo,
`librustc_driver`, `libLLVM`, `rust-lld`, драйвер gcc, `collect2`): **493
различные функции glibc**. По группам: файлы и каталоги 52 (`open`, `openat64`,
`readdir64`, `realpath`, `flock`, `pwritev`, `sendfile64` …), потоки 40
(`pthread_create`, `pthread_cond_timedwait`, `pthread_rwlock_*` …), запуск
процессов 22 (`fork`, `execvp`, `posix_spawn` и его атрибуты), сокеты 21,
локали и текст 15 (`iconv`, `nl_langinfo`, `newlocale`), память 17, **динамическая
загрузка 7 (`dlopen`, `dlsym`, `dlclose`, `dladdr`, `dl_iterate_phdr`,
`_dl_find_object`)** — rustc загружает процедурные макросы как разделяемые
библиотеки.

**Системные вызовы одной настоящей сборки** (`cargo test --no-run -p dep-sched`
под `strace -f`: компиляция и компоновка трёх тестовых исполняемых файлов;
три запуска): **67–69 различных, около 50 000 обращений** (49 665–50 534):

| группа | обращений | вызовов | что |
|---|---|---|---|
| файлы | ~21 900 | 31 | `openat`, `read`, `write`, `statx`, `newfstatat`, `readlink`, `getdents64`, `rename`, `unlinkat`, `flock`, `fcntl`, `ioctl` … |
| синхронизация | ~15 300 | 3 | `futex`, `poll`, `restart_syscall` |
| память | ~6 800 | 5 | `mmap`, `munmap`, `mprotect`, `madvise`, `brk` |
| сигналы | ~4 400 | 4 | `rt_sigaction`, `rt_sigprocmask`, `rt_sigreturn`, `sigaltstack` |
| процессы и потоки | ~2 100 | 21 | `clone3`, `execve`, `wait4`, `prctl`, `arch_prctl`, `rseq`, `set_tid_address` … |
| прочее | ~90 | 3 | `getrandom`, `socketpair`, `recvfrom` |

**Чем это отличается от базового ABI NANOX** (ABI-NCI §4: 14 операций): в нём нет
файлов и каталогов (нужна служба хранилища поверх IPC), нет порождения
процессов и создания потоков (`thread_yield` и `thread_exit` есть, создания нет:
их предстоит дать через `object_invoke` над объектами процесса), нет
`futex` (есть `notification_wait` по маске: ожидание по значению в памяти
придётся собирать поверх него или добавлять примитив), нет `poll` по нескольким
источникам, нет `fork`. `memory_map`/`memory_unmap`, сигнальные и
идентификационные вызовы покрываются или заглушаются.

### Три пути к rustc и cargo внутри NANOX

| путь | суть | цена | главный риск |
|---|---|---|---|
| **A. Порт `std`** под T1 | `library/std/src/sys/nanox`: потоки, замки, время, файлы, процессы, окружение поверх нативного ABI; rustc и cargo собираются под `x86_64-unknown-nanox` | форк библиотеки Rust и всё из пунктов выше в нативном виде; плюс загрузчик разделяемых объектов NANOX для процедурных макросов | объём и поддержка форка; без динамического загрузчика не работают процедурные макросы |
| **B. Личность Linux** | служба, исполняющая неизменённые статические бинарники `x86_64-unknown-linux-musl` и эмулирующая измеренные 67–69 вызовов (и те, что эта сборка не задела) | меньше всего работы в ядре; `dlopen` и загрузчик даёт сама musl, если личность умеет `mmap` файла и `mprotect` | POSIX-модель с неограниченными правами против capabilities NANOX: служба должна быть ограниченным процессом, а не частью ядра |
| **C. Только кросс-сборка** | компилятор остаётся на хосте | ничего | это не self-hosting: критерий M10 не закрывается |

**Предложение (требует согласия владельца и Codex до второго критерия M10):**
B как первый путь к self-hosting, с явным списком внешних зависимостей
(бинарники rustc, cargo, lld и make под musl, собранные вне NANOX; служба
личности), A параллельно и позже, когда ядро, хранилище и процессы созреют;
нативные службы и драйверы остаются на T0/T1 без `std`. Из этого предложения не
следует, что NANOX станет Linux: личность — одна изолированная служба.

Ограничения измерения: glibc-динамический тулчейн Nix, не musl-статический;
сборка крошечного крейта без build-скриптов и процедурных макросов (настоящая
сборка проекта потребует больше: `dlopen`, `mremap`, `sendfile`…); один запуск
на одной машине.

## 7. Что проверено

- `cargo test -p nanox-runtime`: 22 теста; `clippy -D warnings`; сборка под
  `x86_64-unknown-none`. **Мутационная проверка: 25 намеренных ошибок
  (слияние и проверки списка свободных блоков, границы при точном совпадении
  размера, нулевой размер, учёт свободных байт, обратное копирование и флаг
  направления, знак сравнения, границы, перекрытия, имена и дубликаты в блоке
  запуска) — обнаружены все 25.** С первого раза 24: мутант «пустое имя handle
  принимается» выжил, потому что тест портил только первый байт имени и ловился
  проверкой заполнения; добавлен тест имени из одних NUL.
- `python3 -m unittest` в `tools/native`: 13 тестов — контракт ELF (каждое
  правило, 20 000 испорченных файлов без исключений), спецификация целевой
  платформы (поля, отличие от tier-2 только в документированных местах, принята
  rustc), скрипт компоновки, **образец `user/hello`**, собранный
  `tools/native/build.py` под флаги пользователя: 125 КБ, точка входа
  0x400000, три `PT_LOAD` (R+X, R, RW), стек RW, **контракт выполнен**.
- Дизассемблирование `_start`: `xor ebp, ebp; and rsp, -16; call rust_entry; ud2`;
  в образце определены `_start`, `memcpy`, `nanox_main`.

## 8. Что не закрыто (и почему)

Из критериев M10 закрыт только первый — как определение. Остальные требуют
ядра с userspace (M2), хранилища и процессов, которых нет:

| критерий M10 | чего не хватает |
|---|---|
| Compiler, linker, build tools работают внутри NANOX | слой syscall M2 (`abi-user`), процессы, файлы, потоки; путь A или B (раздел 6) |
| ОС пересобирает свои компоненты и образ | предыдущее и M6 (хранилище), запуск `cargo xtask` внутри |
| Ограниченный VMM для испытаний кандидатов | VMM есть на хосте ([M10-VMM](M10-VMM.md)); внутри NANOX нужен драйвер SVM в ядре/службе |
| Обновление и неудачный кандидат с recovery внутри NANOX | M7/M8 и ядро |
| Цепочка с M8 | M8 |

Реализованное здесь не подключено к ядру: `crates/runtime` ждёт
`abi-user`/`abi-types` M2 и согласования startup blob с загрузчиком M2. Имена
крейтов в карте проекта (`runtime`, `abi-user`) совпадают; если Codex создаст свои,
состав модулей нужно сверить, а не дублировать.

## 9. Повторить

```
nix develop --command cargo test -p nanox-runtime
nix develop --command python3 tools/native/build.py         # собирает user/hello, проверяет ELF
cd tools/native && python3 -m unittest -v                   # NANOX_HELLO_ELF=<elf> включает проверку собранного
nix develop --command python3 tools/native/surface.py       # измерение раздела 6 (нужен strace)
```
