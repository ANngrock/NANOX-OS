# M2: пользовательские задачи, вытесняющий планировщик и IPC

Документ фиксирует решения этапа M2 (ARCHITECTURE.md §15) в том объёме,
который реализован и проверен сейчас: критерии 1–3 (пользовательский код в
своём адресном пространстве, вытесняющее переключение задач, IPC с
передачей handle). Критерии 4–6 (проверка аргументов syscall, изоляция
памяти приложений, привилегированная операция Sovereign) в коде частично
есть, но сценариями не проверены — см. [раздел 12](#12-что-не-проверено).

Стенд, harness и формат записи запусков — [m0-bench.md](m0-bench.md);
загрузка, стеки, allocator, таблицы страниц и таймер ядра —
[m1-kernel.md](m1-kernel.md). Конвенции ниже (раскладка GDT, адресное
пространство задачи, ABI системных вызовов, формат handle, правила IPC,
маркеры) в ARCHITECTURE.md не заданы; это решения M2.

## 1. Критерии M2 и их проверка

| --- | --- | --- | --- |
| 1. Пользовательский код запускается в отдельном адресном пространстве | `kernel/task.c` (`nx_utask_create`, загрузка ELF, reap), `kernel/mm/vmm.c` (`nx_as_create`, `nx_as_destroy`), `kernel/mm/pt.c` (`nx_pt_destroy_slots`), `kernel/arch/x86_64/{gdt.c,idt.c,isr.S}`, `lib/elf_plan.c` (`nx_elf_plan_user`), `user/` | сценарий `m2-user`; host-тесты разборки адресного пространства (`test_pt.c`), правил загрузки ELF (`test_elf.c`) и программ из собранного initramfs (`test_initramfs.c`) | проверено |

Готовность M2 целиком («проверены и граница изоляции обычных приложений, и
полный системный статус Core») **не достигнута**: для неё нужны критерии
4–6.

## 2. Где начинается M2 в загрузке

Путь загрузки M1 не изменился ([m1-kernel.md §2](m1-kernel.md#2-последовательность-загрузки-ядра)):
обычная загрузка (`normal`) и все сценарии M1 по-прежнему не запускают
планировщик. Режимы `nanox.test=m2-*` после проверки таймера вызывают
`nx_sched_init` и дальше работают под управлением планировщика:

| Шаг | Маркер |
| --- | --- |
| загрузка M1 до проверки таймера включительно | как в M1 |
| планировщик: поток `kmain` (контекст загрузки), поток `idle`, периодический таймер | `NANOX: sched ok tasks=kmain#1,idle#2 preempt=on slice_ticks=2 hz=100 user_fpu=off gdt_user=0x1b/0x23 syscall_vector=0x80` |
| счётчики ресурсов до теста | `NANOX: <режим> resources before free_pages=... tables=... tasks=2 vmos=0 endpoints=0` |
| создание задач из initramfs | `NANOX: <режим> spawn <имя>#<id> path=bin/<программа> size=... entry=0x0000008000000000` |
| вывод задач | `NANOX: USER <имя>#<id>: <текст>` |
| завершение и освобождение задачи | `NANOX: task <имя>#<id> exited code=... ticks=... preempted=... syscalls=...` |
| счётчики после теста, итог | `NANOX: <режим> resources after ...`, `NANOX: <режим> ok ...`, `NANOX: TEST PASS` |

Контроллер теста — сам поток `kmain` (`kernel/m2test.c`): создаёт задачи,
блокируется до завершения каждой, проверяет результат и счётчики ресурсов и
печатает вердикт. Если задачи не завершились за 20 с (для `m2-sched` — за
60 с), сторожевой таймер планировщика печатает `NANOX: TEST FAIL watchdog:
...` вместо таймаута harness. Он проверяется в прерывании таймера, поэтому
ловит задачи, которые крутятся или ждут, но не зависание самого ядра с
запрещёнными прерываниями — такое останется таймаутом harness.

## 3. GDT, TSS, IDT

Раскладка GDT изменена по сравнению с M1:

| Селектор | Дескриптор |
| --- | --- |
| `0x00` | null |
| `0x08` | код ядра, 64-bit, DPL 0 |
| `0x10` | данные ядра, DPL 0 |
| `0x18` | данные пользователя, DPL 3 (селектор `0x1B`) |
| `0x20` | код пользователя, 64-bit, DPL 3 (селектор `0x23`) |
| `0x28` | TSS (16 байт) |

Порядок пользовательских дескрипторов совпадает с тем, что потребовал бы
`SYSRET`, если его введут позже; сейчас вход в ядро только через `int`.
В TSS, кроме IST-стеков M1, заполняется `RSP0`: при каждом переключении —
верх стека ядра новой задачи. Карта портов ввода-вывода отсутствует,
`IOPL = 0`: пользовательский код не может выполнять `in`/`out`.

IDT: вектор `0x80` — единственный шлюз с DPL 3, то есть единственный, который
пользовательский код может вызвать командой `int`. Остальные векторы
по-прежнему DPL 0. Диспетчер различает источник по `CS & 3`: исключение в
ring 3 завершает задачу (запись `killed: user fault ...`), исключение в
ядре — отчёт и выход 41, как в M1. Путь исключения в ring 3 сценариями этого
шага не проверяется (раздел 12).

## 4. Адресное пространство задачи

Решение M1 «ядро слинковано по физическому адресу в нижней половине,
пересматривается до M2» пересмотрено так: ядро остаётся в слоте 0 PML4,
пользовательская половина начинается со слота 1. Перенос ядра в верхнюю
половину потребовал бы от загрузчика строить таблицы страниц; разделение по
слотам PML4 этого не требует.

| Слоты PML4 | Адреса | Содержимое |
| --- | --- | --- |
| 0 | `0x0`–`0x7FFFFFFFFF` | образ ядра (M1), общий для всех пространств, только supervisor |
| 1–255 | `0x8000000000`–`0x7FFFFFFFFFFF` | пользовательская половина задачи |
| 256–511 | `0xFFFF800000000000`– | ядро: physmap, страница самопроверки VMM, стеки ядра задач |

Внутри пользовательской половины:

| Адрес | Что | Права |
| --- | --- | --- |
| `0x8000000000` (`NX_USER_BASE`) | сегменты программы (`user/user.ld`): `.text`, `.rodata`, `.data`/`.bss` | `r-x`, `r--`, `rw-` (NX) |
| где укажет программа | отображения объектов памяти (`NX_SYS_VMO_MAP`) | `r--` или `rw-` (NX) |
| `0x7FFFFFFE0000`–`0x7FFFFFFF0000` | стек, 16 страниц; `RSP` при входе = `0x7FFFFFFF0000` | `rw-` (NX) |

- `nx_as_create` выделяет новый корень и копирует в него записи PML4 ядра
  (слоты 0 и 256–511). Чтобы все отображения ядра, созданные позже (стеки
  ядра задач, MMIO), сразу были видны во всех пространствах, `nx_vmm_init`
  заранее выделяет PDPT для каждого из слотов 256–511 (256 страниц, 1 MiB).
- Отображения пользователя не глобальные (без `G`), ядра — глобальные. При
  переключении между задачами с разными корнями перезагружается `CR3`, что
  сбрасывает TLB пользовательской половины.
- Страницы программы и стека помечаются программным битом
  `NX_PTE_OWNED` (бит 9, AVL): они принадлежат пространству и освобождаются
  вместе с ним. Страницы объектов памяти этот бит не получают — их освобождает
  объект, когда уходит последняя ссылка.
- Разборка (`nx_as_destroy` → `nx_pt_destroy_slots(1..255)`): обход всех
  листьев пользовательской половины (callback освобождает `OWNED`-страницы),
  освобождение всех таблиц этих слотов и корня. Общие таблицы ядра не
  трогаются. Покрыто host-тестами (`test_pt.c`), в QEMU — сравнением
  счётчиков страниц до и после задачи (раздел 9).
- Ядро никогда не разыменовывает пользовательский указатель: `uaccess.c`
  проверяет диапазон, обходит таблицы страниц задачи (present, user, при
  записи — writable) и копирует через physmap.
- Состояние FPU/SSE при переключении не сохраняется, поэтому оно запрещено в
  ring 3: `CR0.EM = 1`, `CR4.OSFXSR = CR4.OSXSAVE = 0` (x87 даёт `#NM`, SSE —
  `#UD`). Программы собираются с `-mgeneral-regs-only`.

## 5. Задачи и планировщик

`kernel/task.c`, один CPU.

- Задача — объект ядра (`NX_OBJ_TASK`), 32 слота, идентификаторы
  последовательные и не переиспользуются. Состояния: `READY`, `RUNNING`,
  `BLOCKED` (в том числе «создана, ещё не запущена»), `DEAD` (завершилась,
  ресурсы не освобождены), `REAPED` (ресурсы освобождены, слот держат
  ссылки), `FREE`.
- Потоки ядра: `kmain` (контекст загрузки на стеке boot) и `idle`
  (`sti; hlt; cli`). Пользовательская задача — своё адресное пространство,
  свой стек ядра 16 KiB в окне `0xFFFFFE0000000000 + слот × 32 KiB` со
  страницей-ограничителем снизу.
- Round robin по готовым задачам, квант 2 тика таймера (20 мс при 100 Hz).
  Таймер local APIC (M1) после калибровки переводится в периодический режим с
  обработчиком планировщика. По истечении кванта задача вытесняется, если
  готова другая.
- Ядро не вытесняется: системные вызовы и потоки ядра выполняются с
  `IF = 0` и отдают процессор только при блокировке, `yield` или завершении.
  Прерывание таймера переключает задачи, только когда оно пришло из ring 3
  или из `idle`.
- Переключение (`nx_ctx_switch`, `isr.S`) сохраняет callee-saved регистры и
  `RFLAGS` на стеке ядра уходящей задачи; остальное состояние пользователя
  уже лежит в кадре прерывания. Новая пользовательская задача стартует через
  `nx_trap_return`: `iretq` из подготовленного кадра (`CS = 0x23`,
  `SS = 0x1B`, `RFLAGS = 0x202`).
- Завершение: `NX_SYS_EXIT` (или возврат из `umain`) переводит задачу в
  `DEAD` и будит ожидающего. `nx_task_wait_reap` освобождает handles,
  адресное пространство, отображения объектов и стек ядра и печатает строку
  `task ... exited`. Слот остаётся `REAPED`, пока на задачу есть ссылки.

## 6. Системные вызовы (ABI версии 1)

Нормативный заголовок — `abi/nanox/syscall.h`, общий для ядра и программ.

- Вход: `int $0x80`. `RAX` — номер, аргументы в `RDI`, `RSI`, `RDX`, `R10`,
  `R8`; результат в `RAX`: `>= 0` — успех, `< 0` — `-NX_E*`. Все остальные
  регистры и `RFLAGS` сохраняются (восстанавливается весь кадр прерывания).
- Аргументы программы при входе: `RDI`, `RSI`, `RDX`, `RCX`; `RSP =
  0x7FFFFFFF0000` (выровнен на 16). `_start` (`user/rt/start.S`) вызывает
  `umain(a0, a1, a2, a3)`, результат становится кодом выхода.

| № | Вызов | Аргументы → результат | Использован сценариями |
| ---: | --- | --- | --- |
| 1 | `DEBUG_WRITE` | `(buf, len ≤ 256)` → `len` | да, все |
| 2 | `EXIT` | `(code)` → не возвращается | да, все |
| 3 | `YIELD` | `()` → 0 | нет (в ядре `kmain` уступает процессор функцией `nx_yield`) |
| 4 | `TASK_SELF` | `()` → id задачи | да (`hello`) |
| 5 | `HANDLE_CLOSE` | `(h)` → 0 | только ошибка `EBADHANDLE` (`ipc-send`) |
| 6 | `HANDLE_DUP` | `(h, rights ⊆ прав h)` → новый handle; нужно право `DUPLICATE` | только отказ `EACCESS` (`ipc-recv`) |
| 7 | `VMO_CREATE` | `(pages ≤ 64)` → handle с правами `READ WRITE MAP TRANSFER DUPLICATE` | да (`ipc-send`) |
| 8 | `VMO_MAP` | `(h, va, prot)` → 0; нужны `MAP`, `READ`, для записи `WRITE` | да, успех и `EACCESS` |
| 9 | `IPC_SEND` | `(ep, buf, len ≤ 128, h или 0, rights)` → 0; не блокирует | да, успех и `EACCESS` |
| 10 | `IPC_RECV` | `(ep, buf, cap, info*)` → длина; блокирует, пока очередь пуста | да, с блокировкой |
| 11 | `SOV_TASK_OPEN` | `(h Sovereign, id)` → handle задачи | нет (критерий 6) |
| 12 | `TASK_READ` | `(h задачи, va, buf, len)` → `len` | нет (критерий 6) |
| 13 | `TASK_KILL` | `(h задачи)` → 0 | в M3: `bin/core` завершает нагрузку через handle от `SOV_TASK_SPAWN` ([m3-core.md](m3-core.md)) |

Вызовы 14–21 и ошибка `ENOENT` (12) добавлены в M3 —
[m3-core.md §6](m3-core.md#6-ядро-вызовы-1421-события-reaper).

Ошибки: `ENOSYS` (1) неизвестный номер, `EINVAL` (2) размер/флаги,
`EFAULT` (3) буфер не отображён или недоступен, `EBADHANDLE` (4) handle не
выдан, закрыт или устарел, `EWRONGTYPE` (5), `EACCESS` (6) нет нужного
права, `ENOMEM` (7), `EFULL` (8) очередь полна или уже есть получатель,
`EEXISTS` (9) диапазон уже отображён, `ERANGE` (10) адрес вне
пользовательской половины, `EDEAD` (11) задача завершилась.

`DEBUG_WRITE` печатает сразу, с `IF = 0`: каждая строка текста (разбиение по
`\n`, хвост без `\n` — отдельная строка) выходит как
`NANOX: USER <имя>#<id>: <текст>`, байты вне печатного ASCII заменяются на
`?`. Поэтому программа не может напечатать строку, начинающуюся с маркера
ядра (`NANOX: TEST PASS` и т. п.), и строки разных задач не перемешиваются.

## 7. Handles, права, объекты

- Значение handle: биты 0–7 — номер слота + 1 (0 — никогда не handle),
  биты 8–30 — поколение слота, бит 31 — 0. Закрытие и передача увеличивают
  поколение слота, поэтому старое значение отвергается (`EBADHANDLE`) и после
  повторного использования слота (ARCHITECTURE.md §6). Поколение
  циклическое: после 2²³ − 1 закрытий одного слота значение может
  повториться.
- Таблица handle — 32 слота на задачу. Права: `READ`, `WRITE`, `MAP`,
  `TRANSFER`, `DUPLICATE`, `SEND`, `RECV`, `INSPECT`, `MANAGE`, `SOVEREIGN`
  (биты 0–9). **Права можно только сохранить или сбросить** — при
  дублировании и передаче через IPC; добавить нельзя (`EACCESS`).
- Передача — перемещение: у отправителя handle исчезает, ссылка на объект
  переходит в сообщение, а при получении — в таблицу получателя. Передавать
  можно объекты памяти и задачи; endpoint'ы и Sovereign в M2 не передаются.
- Объекты считают ссылки (handle, отображение, сообщение в очереди, ссылка
  ядра). Объект памяти (до 64 обнулённых страниц) освобождает страницы, когда
  уходит последняя ссылка; endpoint при уничтожении освобождает объекты из
  непрочитанных сообщений. Пулы фиксированы: 32 объекта памяти, 16
  endpoint'ов.

## 8. IPC

- Endpoint — очередь на 8 сообщений: до 128 байт данных и не больше одного
  handle. Создаёт их пока только ядро (системного вызова нет); в сценариях
  контроллер кладёт handle с правом `SEND` отправителю и с правом `RECV`
  получателю.
- `IPC_SEND` не блокирует: все проверки (права на endpoint, длина, место в
  очереди, буфер, handle с правом `TRANSFER`, запрошенные права ⊆ имеющихся,
  тип объекта) выполняются до изменения состояния; при отказе handle
  остаётся у отправителя. Затем данные копируются, handle забирается,
  ожидающий получатель будится.
- `IPC_RECV` блокирует задачу, пока очередь пуста; получатель у endpoint'а
  один. Если проверка при получении не прошла (мал буфер, недоступна память,
  полна таблица handle), сообщение остаётся в очереди. Получатель узнаёт
  длину, id отправителя (ставит ядро), значение нового handle и его права
  (`struct nx_ipc_info`).
- В режимах `m2-ipc*` ядро печатает строку на каждую передачу:
  `NANOX: ipc send by <имя>#<id> len=... handle=vmo sender_rights=0x.. requested=0x.. queued=0x..`
  и `NANOX: ipc recv by <имя>#<id> len=... from=#<id> handle=0x.. rights=0x..`.

## 9. Пользовательские программы и initramfs

| Путь | Роль |
| --- | --- |
| `user/rt/start.S` | `_start`: вызов `umain`, затем `NX_SYS_EXIT` |
| `user/rt/nanox_user.h`, `user/rt/rt.c` | обёртки системных вызовов, `u_printf` (подмножество printf через `DEBUG_WRITE`) |
| `user/user.ld` | компоновка с `0x8000000000`, сегменты выровнены на страницу |
| `user/test/*.c` | тестовые программы M2 |
| `abi/nanox/m2test.h` | аргументы и ожидаемые значения, общие для тестовых режимов ядра и программ (не часть системного ABI) |

Сборка (`Makefile`): clang `--target=x86_64-unknown-none-elf`, те же
freestanding-флаги и `-Werror`, что у ядра, плюс `-fpie`: код и данные
адресуются относительно RIP, поэтому программу можно скомпоновать выше 2 GiB
без `-mcmodel=large`. Компоновка `ld.lld -static --build-id=none` (не PIE,
динамических релокаций нет). `lib/string.c` линкуется в программы так же,
как в ядро.

Программы попадают в initramfs как `bin/<имя>`: `mkinitrd.py --file
bin/<имя>=out/build/user/bin/<имя>` (недостающие каталоги создаются, порядок
записей — по пути, как в M1). `make repro-check` сравнивает `initrd.img`, а
значит и программы, побайтово. Ядро при создании задачи проверяет файл
правилами `nx_elf_plan_user`: сегменты внутри `[0x8000000000, стек)`,
размах до 64 MiB, нет сегментов W+X, `p_paddr` не используется.

## 10. Сценарии стенда

Все запускаются `make test` вместе со сценариями M0 и M1.

| Сценарий | `nanox.test=` | Что проверяется | Ожидание (статус QEMU) |
| --- | --- | --- | --- |
| `m2-user` | `m2-user` | `bin/hello`: в своём выводе `cpl=3` (младшие биты CS), четыре аргумента, адреса кода/данных/стека в пользовательской половине, `.data` из файла и обнулённый `.bss`; ядро перед запуском проверяет, что корень таблиц задачи не корень ядра, код отображён `user,r-x`, стек `user,rw-`, а в таблицах ядра этих адресов нет; после reap `free_pages`, `tables`, `tasks` равны значениям до создания задачи (harness сверяет их обратной ссылкой в регулярном выражении) | PASS (33) |
| `m2-sched` | `m2-sched` | три `bin/spin` по 2·10⁸ итераций xorshift64 без `yield` и блокировок; ядро заранее считает ожидаемый результат тем же циклом; каждая задача печатает 4 строки прогресса и результат; ядро требует: код выхода 0 (результат совпал), 0 вызовов `yield`, каждая задача вытеснена хотя бы раз, **первая строка прогресса каждой задачи раньше последней строки любой задачи**; harness независимо проверяет то же чередование по serial-логу (`interleave`) и совпадение результатов с ожиданием ядра | PASS (33) |
| `m2-sched-nopreempt` | `m2-sched-nopreempt` | отрицательный контроль: те же задачи с выключенным вытеснением идут строго друг за другом, проверка чередования обязана сработать | `test_fail` (35), `tasks did not interleave`, `preempted=0,0,0` |
| `m2-ipc` | `m2-ipc` | `ipc-recv` запускается первым, ядро дожидается, что он заблокирован в `IPC_RECV`, и только тогда запускает `ipc-send`; `ipc-send` создаёт объект памяти (права `0x1f`), заполняет страницу, пробует передать handle с лишним правом `SEND` (`EACCESS`, handle остаётся), передаёт с правами `READ\|MAP` (`0x5`), после чего его handle недействителен (`EBADHANDLE`); `ipc-recv` получает сообщение без искажений, id отправителя и handle ровно с `0x5`, отображает страницу только для чтения и видит данные отправителя (разрешённая операция), отображение на запись и дублирование получают `EACCESS`; после обеих задач объект памяти и endpoint уничтожены, страницы возвращены | PASS (33) |

Повторяемость: `harness.py repeat m2-sched --count 3` (часть `make test`).
Строки задач (`NANOX: USER ...`) в разных запусках чередуются по-разному,
поэтому сценарий объявляет их неупорядоченными (`"repeat": {"unordered":
"^NANOX: USER "}`): они сравниваются как мультимножество — те же строки прогресса
и те же итоговые строки `done ... result=... ok` каждой задачи в том же
количестве. Остальные маркеры сравниваются по порядку, как в M1; кроме
измерений времени маскируются статистики планирования (`preempted=`,
`preemptions=`, `switches=`, `latest_first=`, `earliest_last=`).

Отрицательные контроли показывают, что проверки чувствительны: без
вытеснения проверка чередования не проходит (в ядре — в самом сценарии; в
harness — это проверено вручную на логе `m2-sched-nopreempt` и unit-тестами
`test_harness.py`), а выдача лишних прав обнаруживается получателем.

## 11. Что проверено при подготовке этого шага

Эталонная среда та же, что в M0 и M1 (Ubuntu 24.04, clang/lld 18.1.3,
QEMU 8.2.2, TCG, без KVM). Выполнено в рабочем дереве и в свежем
`git clone`:

- `make doctor && make && make test` — код выхода 0: host-тесты C
  (616 проверок, UBSan в режиме trap), 37 Python-тестов, 26 сценариев QEMU
  (8 M0, 13 M1, 5 M2) с ожидаемыми вердиктами, повторяемость `normal`,
  `pagefault` и `m2-sched` (по 3 запуска, маркеры совпали; для `m2-sched` —
  80 упорядоченных строк и 15 строк задач как мультимножество);
- host-тесты дополнительно собраны gcc с `-fsanitize=address,undefined`;
- в проверяемый host-тестами код по одной вносились 17 ошибок (права при
  дублировании и передаче, поколения handle, граница таблицы, счётчик
  ссылок, переполнение и перенос очереди, утечки при разборке таблиц,
  лишний слот, пропуск листьев, W+X, зарезервированный бит) — каждую тесты
  обнаружили;
- `make repro-check` — `BOOTX64.EFI`, `kernel.elf`, `initrd.img` (с
  программами `user/`) и `nanox.img` побайтово совпали в трёх сборках;
- `make debug-check` — GDB остановился в `kernel_main`.

## 12. Что не проверено

**Критерии 4–6 — реализовано в коде, тестами пока не проверено.**

- Критерий 4 (некорректный syscall не повреждает ядро). В коде: номер и
  аргументы сравниваются как 64-битные значения, размеры ограничиваются до
  использования, handle разрешаются через таблицу вызывающей задачи с
  проверкой типа и прав, пользовательская память — только через
  `uaccess.c`. Сценариев с некорректными аргументами нет; переключатель
  внедрения ошибки `nx_inject_uaccess_unchecked` ни одним режимом не
  включается; host-тестов `uaccess.c` нет.
- Критерий 5 (приложение не читает память другого). В коде: у каждой задачи
  свой корень таблиц, пользовательские страницы есть только в нём; страницы
  ядра без бита U. Сценария, где задача пытается прочитать чужую или ядерную
  память, нет; путь «исключение в ring 3 → задача завершена»
  (`nx_user_trap`) не выполнялся.
- Критерий 6 (Sovereign). В коде: объект `nx_sovereign()` и вызовы
  `SOV_TASK_OPEN`, `TASK_READ`, `TASK_KILL`. В M2 ни один режим не выдаёт
  задаче handle Sovereign. С M3 handle Sovereign получает `bin/core`, и
  сценарии M3 выполняют `TASK_KILL` над запущенной им нагрузкой
  ([m3-core.md](m3-core.md)); `SOV_TASK_OPEN` и `TASK_READ` по-прежнему не
  выполнялись, и критерий 6 как проверка M2 не оформлен.

Прочее:

- Не выполнялись: `YIELD` из ring 3, успешные `HANDLE_CLOSE` и
  `HANDLE_DUP` из ring 3 (логика таблицы покрыта host-тестами), `IPC_SEND`
  без handle, передача handle задачи, завершение чужой задачи.
- Исчерпание ресурсов (32 задачи, 32 handle, полная очередь, нехватка
  памяти при создании задачи или отображении) в QEMU не проверялось;
  полная таблица handle и полная очередь покрыты host-тестами.
- Страница-ограничитель стека ядра задачи и сообщение о её срабатывании не
  проверены.
- Циклический счётчик поколения handle допускает повтор значения после
  2²³ − 1 закрытий одного слота.
- Ядро не вытесняемо; один CPU; FPU/SSE в ring 3 запрещены; endpoint'ы
  создаёт только ядро.
- Вытеснение проверено при 100 Hz и кванте 20 мс под TCG; справедливость
  планировщика и задержки не измерялись.
- Все результаты получены в QEMU (TCG) и не доказывают работу на реальном
  оборудовании.
