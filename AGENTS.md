# Работа над NANOX-OS

Пользовательские указания имеют приоритет. Этот файл задаёт правила разработки проекта, а не полномочия изменять чужие проекты, диски или настройки компьютера.

## Прочитать перед работой

1. `docs/START-HERE.md` (историческая постановка M0: читать для контекста, не исполнять повторно) и `docs/STATUS.md`.
2. `docs/adr/0001-platform.md`.
3. Спецификацию текущего этапа в `docs/specs/` и его критерии в `docs/ROADMAP.md`.

M0 завершён для проверенного QEMU/OVMF-профиля (доказательства — `docs/STATUS.md`). По указанию пользователя приоритет — M5: ранние срезы M5, проверяемые на host без ядра и userspace (контракт `docs/specs/M5-NETWORK.md`), идут первыми; M1–M4 остаются обязательными зависимостями для завершения M5 и выполняются следом. Срезы и порядок — по `docs/STATUS.md` и `docs/ROADMAP.md`. Не подменять его новым обсуждением выбора языка, модели или имени проекта. Разумные подробности реализации решать самостоятельно и фиксировать; существенные отступления оформлять ADR с основанием.

## Неизменяемые требования

- Собственное ядро NANOX; Linux используется только как host разработки.
- Rust `no_std` для loader/kernel; Rust для сервисов; ASM только там, где требуется машинный интерфейс.
- В loader/kernel нет сторонних прикладных crates. Собственные workspace-crates и поставляемый Rust sysroot разрешены. `alloc` используется только после реализации allocator.
- Cognitive Core обладает абсолютными программными полномочиями внутри NANOX. Не заменять это скрытым списком разрешённых задач.
- Обычные приложения изолируются; локальный исполнитель Core является доверенным системным субъектом.
- Все действия и результаты должны различаться: текст модели не подтверждает изменение машины.
- Не объявлять внутренние логи или копии защищёнными от самого Sovereign.

## Рабочая среда

- Основной build-checkout — на Linux filesystem в WSL. Не запускать тяжёлые сборки из `/mnt/c`/OneDrive.
- До создания нового checkout найти существующий, проверить Git-ревизию, ветку, remote и изменения. Перенести необходимые незакоммиченные материалы без потерь и назначить один основной checkout.
- Не создавать второй независимый репозиторий с отдельной историей под тем же именем.
- Сведения из старой беседы о WSL, Nix, USB, `dd` и номерах дисков — непроверенные до текущего осмотра среды.
- Не выполнять автоматически `wsl --unmount`, остановку WSL, остановку неизвестного процесса, форматирование или запись на физический диск. M0 использует файлы образов внутри checkout; аппаратные действия требуют актуальной идентификации цели и соответствующего задания пользователя.
- PSW-OS не входит в задачи NANOX.

## Качество реализации

- Писать законченные небольшие изменения. Не создавать дерево пустых модулей вместо работающего сценария.
- У каждого `unsafe` — локальное объяснение инвариантов адреса, выравнивания, длины, владения, времени жизни и конкурентного доступа, где применимо.
- Не ссылаться на Rust layout по умолчанию через ABI; использовать явно заданные поля и представление.
- Не передавать Rust references, `String`, `Vec` или trait objects через syscall/wire-границу.
- Проверять размеры, переполнения, пересечения диапазонов и переходы состояний до эффектов.
- После успешного `ExitBootServices` не вызывать Boot Services и не использовать их allocator.
- Для interrupt/syscall entry использовать стабильный ASM-путь. Не включать nightly только ради `extern "x86-interrupt"`.
- Kernel panic, ошибка загрузки, ошибка теста и ошибка harness должны различаться.
- Зависание не считается успехом; тесты имеют внешний timeout.

## Проверки и доказательства

- Выполнять проверки текущего этапа; отдельно негативные сценарии для loader, границ памяти и полномочий.
- Не писать тесты, которые лишь повторяют код. Проверять поведение на границах, ошибках и сбоях.
- Сохранять сырой serial, stderr QEMU, argv, версии, хеши и вердикт.
- Различать обычный повторный запуск, повторяемую сборку и настоящий record/replay.
- Не вычищать строки лога, чтобы искусственно получить равенство replay.
- Моки провайдера пригодны для тестирования task engine; демонстрация ИИ требует настоящей модели.
- QEMU, API bridge, внешняя сборка и нативное выполнение — разные режимы, маркировать их честно.
- Обновлять `docs/STATUS.md` с командами и путями к доказательствам; отмечать чекбоксы только по выполненным проверкам.

## Git и отчёт

- Сначала `git status`; сохранять изменения пользователя.
- Новые рабочие ветки именовать `codex/...`, если пользователь не задал другое имя.
- Не выполнять destructive reset/clean и не пушить без соответствующего задания.
- Не добавлять секреты, реальные API-ключи, огромные образы, `target/` и журналы с чувствительными данными в Git.
- В отчёте писать: что работает, что проверено, где артефакты, что не работает, следующий незавершённый критерий.
- Не превращать обычное завершение этапа в повторный запрос согласовать уже выбранную архитектуру.
