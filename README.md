# NANOX-OS

Самостоятельная ОС с собственным ядром, системными сервисами и встроенным
Cognitive Core. Архитектура и план этапов — [ARCHITECTURE.md](ARCHITECTURE.md).

Текущее состояние: этапы **M0 «Воспроизводимый стенд»**, **M1 «Собственная
загрузка и ядро»** и **M4 «Постоянное состояние»** выполнены (M4 — в модели
сбоя QEMU, см. ниже), этапы **M2 «Изоляция, потоки и IPC»** и **M3 «Первый
замкнутый цикл ИИ»** — частично.
Собственный UEFI-загрузчик (C17, PE/COFF) проверяет и загружает ядро
(freestanding C17 + ASM, ELF64) и initramfs (cpio newc) и передаёт boot info
1.1. Ядро ставит свои GDT/TSS/IDT, стеки со страницами-ограничителями,
физический allocator, свои таблицы страниц (W^X, physmap), таймер local APIC
и выдаёт проверяемые отчёты о panic и исключениях. С M2 ядро запускает
программы из initramfs в ring 3, каждую в своём адресном пространстве,
переключает задачи вытесняющим планировщиком по таймеру и передаёт между ними
сообщения и handle с уменьшенными правами. Проверены критерии M2 1–3;
критерии 4–6 (проверка аргументов syscall, изоляция памяти приложений,
Sovereign) реализованы в коде частично и тестами пока не проверены — см.
[docs/m2-kernel.md](docs/m2-kernel.md).

С M3 в ядре есть журнал событий состояния задач и управляющие системные
вызовы, а исполнитель Cognitive Core (`bin/core`, ring 3, handle Sovereign)
принимает запросы NCI от host bridge по второму последовательному порту,
исполняет их через ядро, проверяет конечное состояние и ведёт task engine с
дедупликацией запросов. Host bridge (`tools/bridge/`) переводит решения
адаптера модели в запросы NCI и пишет трассу. Проверены критерии M3 1, 2, 4,
5, 6 — с мок-моделью; настоящая модель не подключалась, поэтому критерий 3 и
готовность M3 не подтверждены — см. [docs/m3-core.md](docs/m3-core.md).

С M4 у ядра есть драйвер virtio-blk (PCI, virtio 1.x, опрос), а у
исполнителя — постоянное хранилище `nxstore` на втором диске QEMU:
copy-on-write с двумя слотами суперблока, поколениями, версиями объектов,
журналом фиксаций, окном хранения и закреплениями поколений. Поколение
объявляется сохранённым только после второго flush протокола фиксации.
Исполнитель хранит там конфигурацию, историю и записи своего task engine
(прерванные действия после перезапуска — `OUTCOME_UNKNOWN`, повтор запроса
прежней загрузки отвечается из записи). Проверены все четыре критерия M4:
серия сбоев останавливает рабочую нагрузку перед каждой из её операций
записи и flush с разными политиками потери незафиксированных записей и
каждый раз находит допустимое целое состояние; проверены также повреждённый
корень, полный диск, политика хранения и независимое чтение диска
host-реализацией формата. Настоящее отключение питания и реальное
оборудование не проверялись — см. [docs/m4-store.md](docs/m4-store.md).

## Быстрый старт

Требования (эталонная среда Ubuntu 24.04):

```sh
sudo apt-get install clang lld qemu-system-x86 ovmf mtools python3 make gdb
```

Затем из чистого checkout — одна последовательность:

```sh
make doctor && make && make test
```

- `make doctor` сверяет версии инструментов и хеши прошивки с `toolchain.lock`;
- `make` собирает `out/BOOTX64.EFI`, `out/kernel.elf`, `out/nanox.img` и
  диск данных `out/data.img` (M4);
- `make test` запускает host-тесты, все сценарии QEMU (включая серию сбоев
  M4, около 5 минут на 4 CPU; параллельность — `NANOX_JOBS`) и проверку
  повторяемости; каждый запуск записывается в
  `out/runs/<время>-<сценарий>/record.json`.

Прочие цели: `make run` (одна загрузка с выводом serial), `make debug` +
`gdb -x tools/gdb/nanox.gdb` (отладка), `make repro-check` (побайтовая
воспроизводимость). Окружение Nix описано в `flake.nix`, но ещё не проверено
(см. [docs/m0-bench.md](docs/m0-bench.md#3-toolchain)).

## Структура

```text
abi/nanox/        общие форматы: boot info, манифест, коды диагностики, ABI системных вызовов
boot/uefi/        UEFI-загрузчик
kernel/           ядро: arch/x86_64 (вход, GDT/IDT, исключения, таймер, переключение
                  контекста, link map), mm (allocator, таблицы страниц, адресные
                  пространства, доступ к памяти пользователя), obj (handles, IPC, объекты),
                  dev (PCI, virtio-blk, блочное устройство и слой сбоев M4),
                  задачи и планировщик, системные вызовы, события состояния, канал bridge
                  (COM2), тестовые режимы M2, M3 и M4, initramfs, panic
user/             программы ring 3: rt (вход, обёртки syscall), test (тестовые программы M2,
                  нагрузка M3), core (исполнитель Cognitive Core: NCI, task engine,
                  постоянное состояние M4)
initrd/           содержимое initramfs (программы из user/ добавляются в bin/ при сборке)
lib/              freestanding-код загрузчика, ядра и программ: serial, printf, SHA-256,
                  CRC-32, mem*, план загрузки ELF, хранилище nxstore (M4)
tools/image/      детерминированные писатели образа GPT + FAT32 и initramfs
tools/bench/      конфигурация QEMU, harness, символизация, проверка GDB, проверки
                  хранилища и серия сбоев M4
tools/bridge/     host bridge M3: клиент NCI, адаптеры модели, цикл агента, трасса;
                  сценарии host M4
tools/store/      независимая host-реализация формата nxstore (создание диска данных,
                  чтение, проверка, повреждения для сценариев)
tools/doctor.py   проверка окружения по toolchain.lock
tests/host/       host-тесты (C и Python)
tests/qemu/       сценарии стенда
```
